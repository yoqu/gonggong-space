# HTTPS and certificates

This page explains why Gonggong Space requires HTTPS, how to set up either of the two certificate options, and what the daemon's certificate fingerprint pinning means when you change certificates.

## Why HTTPS is required

- **The daemon only connects to non-local servers over `https://`.** `http://` is accepted only for loopback addresses (`localhost`, `127.0.0.0/8`, `::1`), for local development; any other address fails with 「只允许通过 https:// 连接非本机服务器」 ("only https:// connections to non-local servers are allowed").
- The session cookie needs the `Secure` flag under HTTPS.
- Features such as browser push notifications are only available in a secure context (HTTPS).

## Daemon certificate pinning

The daemon doesn't rely on the CA chain. Instead, it **pins the SHA-256 fingerprint of the server's leaf certificate**:

1. When a member binds with `gg login`:
   - With `--fingerprint sha256:AB:CD:…` (or using a connect link generated on the web, which includes the fingerprint): only a certificate with that fingerprint is accepted.
   - Without a fingerprint: trust on first use. The fingerprint of the certificate seen at that moment is written to the local config and printed; the member should check it against the value published by the admin.
2. From then on, every HTTPS and WebSocket connection the daemon makes is checked against that fingerprint. On a mismatch it refuses to connect and reports 「服务器证书指纹不匹配，拒绝连接」 ("server certificate fingerprint mismatch, connection refused").

This makes a self-signed certificate as safe as a public CA certificate, and the daemon can't be impersonated by a man in the middle just because the operating system trusts some CA. For command usage, see [Command reference](/en/cli/reference).

::: warning New certificate = new fingerprint
What's pinned is the **entire leaf certificate**, not the CA or the public key. After a certificate is renewed or replaced (including Let's Encrypt auto-renewal), the fingerprint changes and every bound daemon refuses to connect. When that happens:

1. Publish the new certificate's fingerprint.
2. Each member generates a new bind code on the web and runs `gg login` again to rebind (existing machine records and Bots are restored automatically).

Take this into account when choosing a certificate option. See [Renewal and replacement](#renewal-and-replacement) below.
:::

## Check the certificate fingerprint

```bash
openssl x509 -in cert.pem -noout -fingerprint -sha256 | sed 's/.*=/sha256:/'
```

For files containing a certificate chain (such as Let's Encrypt's `fullchain.pem`), `openssl x509` reads only the first certificate, which is the leaf certificate—exactly the one the daemon pins.

`gg login --fingerprint` accepts `sha256:AB:CD:…`, `AB:CD:…`, or 64 hex digits without colons, in either case.

## Option 1: public domain with a trusted certificate

For production deployments facing the internet: Nginx terminates HTTPS with a certificate issued by a public CA such as Let's Encrypt, and the server listens locally over HTTP only.

1. Get a certificate for the main site's domain (such as `gg.example.com`). A single-domain certificate can use HTTP-01 validation (`certbot --nginx` or `acme.sh --nginx`); a wildcard certificate for the preview domain can only use DNS-01. See [Reverse proxy and preview domains](/en/deploy/reverse-proxy#wildcard-certificate).
2. Configure the certificate in Nginx and reverse-proxy to `http://127.0.0.1:8787`. See [Reverse proxy and preview domains](/en/deploy/reverse-proxy).
3. On the server, **do not set** `GONGGONG_TLS_CERT` / `GONGGONG_TLS_KEY`, but you must set:
   ```ini
   GONGGONG_SECURE_COOKIES=1
   GONGGONG_PUBLIC_URL=https://gg.example.com
   ```
4. Compute the fingerprint of the certificate Nginx uses with the command above and publish it to members.

With this option the server has no certificate of its own, so the commands and connect links generated by 「绑定新机器」 (Bind new machine) on the web **don't include a fingerprint**. On first bind the daemon trusts the Nginx certificate it sees and prints the fingerprint for you to verify.

## Option 2: self-signed certificate on a LAN

For intranets or LANs without a public domain: use a self-signed certificate, and the connect link carries the fingerprint to the daemon automatically.

### Generate a self-signed certificate

The repository includes a script that generates a self-signed certificate covering `localhost`, `127.0.0.1`, and every LAN IPv4 address of the machine (valid for 825 days):

```bash
bash scripts/dev-cert.sh              # outputs to .gonggong-dev/tls/ by default
bash scripts/dev-cert.sh /etc/gonggong/tls   # or specify a directory
```

The script prints two lines:

```text
GONGGONG_TLS_CERT=/…/cert.pem GONGGONG_TLS_KEY=/…/key.pem
sha256:AB:CD:…
```

Set the first line as the server's environment variables; the second line is the fingerprint to publish. Once set, the server **serves only HTTPS/WSS** on the same port, the session cookie gets `Secure` automatically, and connect links generated on the web include the fingerprint automatically.

If you issue the certificate from your own domain or an internal CA, just put the certificate and private key paths into the same two variables.

### Try it with the dev server

If you're only trying it out on a LAN without Nginx, the web dev server reads the same pair of variables, serves over HTTPS, and proxies to the server:

```bash
export GONGGONG_TLS_CERT=… GONGGONG_TLS_KEY=…
GONGGONG_ADMIN_PASSWORD=<initial-password> pnpm dev:server
WEB_HOST=0.0.0.0 pnpm dev:web          # members open https://<this machine's LAN IP>:5173
```

The browser will warn that the certificate isn't trusted; confirm to continue.

### Use it with Nginx

A proper intranet deployment still needs Nginx to host the web app. **Have Nginx use exactly the same certificate files as the server**, so the certificate the daemon sees matches the fingerprint in the connect link:

```nginx
ssl_certificate     /etc/gonggong/tls/cert.pem;
ssl_certificate_key /etc/gonggong/tls/key.pem;

location ~ ^/(api|ws|livekit|downloads)(/|$) {
    proxy_pass https://127.0.0.1:8787;   # the server has TLS enabled, so the upstream uses https
    proxy_ssl_verify off;
    # other proxy_set_header lines etc. same as on the "Reverse proxy" page
}
```

If Nginx and the server use different certificates, the fingerprint in the connect link won't match what the daemon actually sees, and binding fails. In that case, have members bind with the command without `--fingerprint` and verify the fingerprint manually.

## Renewal and replacement

| Certificate | Validity | Impact on daemons |
| --- | --- | --- |
| `dev-cert.sh` self-signed | 825 days | Replace manually before expiry and notify members to rebind once |
| Let's Encrypt | 90 days, usually auto-renewed every 60 days | Members must rebind after every renewal |
| Other public CAs | As issued | Members must rebind after every replacement |

::: tip
Before changing certificates, notify members in a group and have the new fingerprint ready. To rebind, members just run `gg login`; existing machine records and Bot bindings stay the same. Desktop app users paste the bind command again in the app. See [Desktop app onboarding](/en/desktop/onboarding).
:::

## For development: disable certificate pinning

Setting `GONGGONG_INSECURE_DEV=1` on a member's machine disables certificate pinning (the daemon prints a prominent warning). Connections can then be impersonated by a man in the middle, so **use it only for local development**.
