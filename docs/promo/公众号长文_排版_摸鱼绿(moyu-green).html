产品经理提的需求，我让他直接 @ 我的电脑改

国庆基本是家里蹲，这几天把一个憋了挺久的东西肝出来了，叫共工空间。它是开源的，代码在 GitHub 上。这篇想把它为什么做、长什么样、几个关键设计是怎么想的，完整说一遍，篇幅有点长，可以先收藏。

节 01AI 编程进了团队以后，反而更别扭了

我们团队现在写代码基本离不开 Claude Code 和 Codex。一个人用的时候是真爽，但几个人一起干活，问题就冒出来了：

上下文是割裂的。 我让 Agent 改了个接口，队友那边的 Codex 完全不知道，还得我去群里喊一声「接口改了啊」。每个人的 Agent 都只知道自己终端里那点事。

环境是重复的。 我机器上仓库、依赖、各种登录态都配好了，队友想让它跑点东西，要么来找我，要么自己从头配一遍。一台配好的电脑，只能服务它的主人。

结果是看不见的。 Agent 说「服务已经起来了」，可它只监听在我本机的 localhost，别人根本打不开。想给别人看个效果，还得截图、录屏、或者折腾内网穿透。

还有一个更痛的：需求要转述两遍。 产品经理提了需求，我得先理解一遍，再原样讲给 AI 听。很多时候我在这一步里什么判断都没加，纯粹是个传话筒。

节 02为什么不直接用云端 Agent

这两年大厂都在做云端 Agent，把代码拉到云上的沙箱里跑。思路没问题，但放到我们这种小团队里，有几个不顺手的地方：

• 云上的沙箱是干净的，可我们真正干活的环境在自己电脑上：私有依赖、内网服务、各种登录态、甚至只在某台 Mac 上才能跑的模拟器。

• 代码和模型 Key 要交给第三方，有的团队过不了这一关。

• 办公室里其实有一堆闲着的电脑。

所以我想做的是一个「类云电脑」的东西：不把代码搬上云，而是把大家的电脑组个队。 团队里每个人的电脑、甚至角落里吃灰的那台，都接进来，大家在一个群里沟通，Agent 也拉进群。谁要干活，就 @ 谁的电脑。

这样上下文天然是对齐的（大家在同一个群里聊），环境也不用重复配（直接用主人那台配好的电脑）。产品经理的需求可以直接 @ 我的电脑去改，我只管最后的代码审批和需求审批。

节 03用起来是什么样

举个演示环境里的例子。群「todo-app 开发群」里有三个人、三个 Bot：前端小助手是王磊 Mac 上的 Claude Code，后端助手是一个 Codex，还有一个测试助手。

群聊主界面

王磊在群里发：「@前端小助手 给待办列表加一个『只看未完成』的筛选按钮，选择记在 localStorage 里，README 补一句说明。」

接下来发生的事，群里每个人都看得到：

1. 前端小助手在王磊的电脑上开工，思考、读了哪些文件、改了哪些地方，实时刷在群里。

2. 它想执行 git commit，这超出了它「工作区可写」的权限，群里弹出一张审批卡片，只有 Bot 主人王磊能点「批准」。

3. 改完以后，它把服务跑起来，发了一张预览卡片。李娜点开，右边直接就是页面，可以点、可以切换筛选，回了一句「交互没问题」。

4. 李娜让后端助手顺手看一眼 server.js，它发现一个路径穿越问题，在群里说明了结论，没有乱改代码。

预览工作台

整个过程没有人截图、没有人转述、也没有人去配别人的环境。这就是我想要的样子。

除了这条主线，还有几个我觉得挺实用的能力：

• 跑的过程中可以插话。 追加一条消息就能改方向，/stop 直接叫停。没 @ 的群消息也会当作背景带给 Bot，前面讨论过的需求不用再复述。

• Bot 之间能接力。 后端改完接口，可以把活甩给前端 Bot 接着改页面。拿不准的时候，它会在群里出一道选择题问人。

• 不只是网页能预览。 Electron、Tauri 这类桌面应用的窗口，微信开发者工具里的小程序模拟器，都能实时推到群里，别人还可以申请远程点一点。

• 定时任务。 比如每天早上让 Bot 跑一遍回归、汇总昨天的提交，到点它自己 @ 合适的 Bot 去干。

• 飞书里也能用。 扫码建个应用，飞书群里一样 @ Bot，运行过程会像打字一样一点点刷出来。

节 04几个关键设计是怎么想的

这部分偏技术，不感兴趣可以直接跳到第五节。

系统架构

整体就三块：浏览器、服务器、每台电脑上的 daemon。服务器用 Fastify + PostgreSQL，daemon 用 Rust 写，命令叫 gg，桌面端里也内置了一份。

1. 服务器不碰 Key 和代码

这是我最先定下来的一条。服务器只管账号、转发消息、派活、中继和审计；代码读写、命令执行全在成员自己的电脑上；模型 Key、Agent 登录态、git 凭据也只留在本机。

服务器能看到的，只有 Agent 回传的过程、最终回复和这一轮的 diff，入库前会脱敏，过程和 diff 加密存储。换句话说，就算服务器被人拿走了，他也拿不到你的 Key。

2. daemon 只往外连

所有连接都是 daemon 主动连服务器的：一条 WebSocket 收任务、回传事件，另一条做预览隧道。成员电脑不用开任何端口，家里的 NAT、公司的防火墙都不用管，也不用折腾内网穿透。

这也是「组队」能成立的前提：只要那台电脑能上网，就能接进来。

3. 用 ACP，不去解析终端输出

一开始也想过直接包一层 CLI，解析它的终端输出。试了一下就放弃了，太脆，CLI 一升级可能就挂。

后来换成了 ACP（Agent Client Protocol）。Claude Code 和 Codex 各有一个官方适配器，思考、工具调用、权限请求都是结构化事件，daemon 拿到就能直接用。以后要接别的 Agent，加一个适配器就行。

每个「群 × Bot」对应一个会话和一个独立工作区。适配器空闲 10 分钟就回收，下一轮在新进程里恢复会话，Bot 还记得之前聊过什么。

4. 群协作的能力，都通过一个 MCP 给 Agent

Agent 怎么知道群里聊过什么、怎么在群里提问、怎么发预览、怎么把活交给别人？

答案是 daemon 在本机给每个会话起一个叫 gonggong 的 MCP。Agent 通过它翻群聊记录、查成员和运行记录、在群里出选择题、发布预览、把任务交给别的 Bot、创建定时任务。对 Agent 来说，这就是一组普通的工具；对我来说，群协作的能力只需要在一个地方维护。

5. 预览怎么进群

网页类预览走隧道：浏览器访问服务器上的预览入口，服务器通过 daemon 维持的长连接转发到成员电脑的本地端口，HTTP 和 WebSocket 都能通。要给团队外的人看，可以生成一个限时的公开链接，到期自动失效，也能随时收回。

桌面应用和小程序走另一条路：daemon 只抓那一个应用的窗口推流，不会把整个屏幕推出去，而且有人在看才推。远程操控同一时间只有一个人，普通成员要先申请，Bot 主人或群管理员同意了才行。

6. 几台电脑改同一份代码：不用锁，用乐观并发

默认情况下，每个 Bot 在自己的工作区里干活，改动各管各的，要合并就按团队的 git 流程走。

但有些场景，大家希望几台电脑上的 Bot 改的是同一份代码，于是做了「强制同步」。最早的方案是群锁：谁要改就先拿锁，其他人排队。写到一半发现太别扭了，Bot 大部分时间都在排队。

后来改成了乐观并发：

• 各个 Bot 照常并行干活，每轮结束把改了哪些文件提交上去，每个文件带着「我开工时它长什么样」的哈希。

• 服务器逐个文件比对：没人动过就直接合入，生成一个新版本，再分发给其他电脑。

• 撞车了，文本文件先在本机自动做三方合并，合干净了就重新提交；合不了才交给群管理员或 Bot 主人，一个文件一个文件地选。

• Agent 干活期间，它的工作区不接收新版本，避免文件在它手底下被改掉；这一轮结束后再一起补齐。

我拿一个 10 万文件的仓库在两台电脑之间测过，能跑通。

7. 让别人 @ 你的 Bot，就是让别人在你电脑上跑 Agent

这句话我写在了文档的安全须知里，因为它是整个产品风险最大的地方，所以这块做得比较保守：

• 权限分三档：只读、工作区可写、完全访问。越档的操作会弹审批卡片，只有 Bot 主人能批。

• 谁能 @ 也能设：只有自己、指定的人、或者群里所有人。

• Bot 默认在隔离的托管工作区里干活，所有操作都有审计。

越档操作由 Bot 主人审批

我自己的建议还是：拿一台专用电脑或虚拟机跑 Bot，日常工作机别对群开「完全访问」。

节 05国内用起来

做的时候特意照顾了一下国内的网络：

• 默认走 npmmirror，daemon 能一键装好 Node、Claude Code、Codex。

• 常见的模型厂商都内置了预设，选一下、填个 Key 就能用；用 CC Switch 的话，可以直接导入配置。

• 客户端有命令行 gg（macOS / Linux / Windows），也有 macOS 和 Windows 桌面端，带托盘和自动更新。

节 06怎么试

最省事的是去演示环境注册一个账号：gg.uyoqu.com，绑定自己的电脑就能玩。演示环境只供体验，别放敏感代码。

自己部署的话，服务端用 Docker 一条命令就能起来：

git clone https://github.com/yoqu/gonggong-space.git && cd gonggong-space

GONGGONG_ADMIN_PASSWORD=初始密码 docker compose up -d

打开网页登录，右上角「绑定新机器」，复制命令到要跑 Bot 的电脑上执行。然后建个 Bot、拉个群、@ 它干活。一台电脑也能玩起来。

节 07现在的不足

说点实在的：

• 现在是 v0.3.0，从国庆前到现在发了三个版本，肯定还有不少毛病。

• 目前只支持 Claude Code 和 Codex。

• 它不是一个通用的团队聊天工具，定位就是「几个人一起用 Agent 干活」，日常聊天还是用你们现在的 IM 更合适。

• 安全这块我心里最没底，欢迎懂行的朋友来挑刺。

节 ∞最后

共工空间现在还不是一个完美的东西，更像是一个正在长出来的「团队 Agent 工作台」。如果你们团队也是每个人各开一个终端跑 Agent、需求在群里传来传去，希望它能帮你们少折腾一点。

项目是 Apache-2.0 开源的，会一直维护。最想听听大家团队里会不会这么用、卡在哪，欢迎在 GitHub 提 Issue，也欢迎直接在评论区吐槽。
