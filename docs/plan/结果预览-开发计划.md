# 结果预览开发计划：服务托管、端口隧道与桌面应用推流

目标：agent 在 daemon 本机做出的结果（网页、端口服务、桌面应用），群成员能在聊天里直接看、直接用，也可以生成外部公开链接。不引入 frp 这类独立的穿透组件，复用 daemon 和 server 之间已有的长连接。

## 1. 现状

| 项 | 现状 |
| --- | --- |
| daemon 连接 | daemon 主动连 `/ws/daemon`（`apps/server/src/daemon/gateway.ts`、`hub.ts`），按 machineId 维护单连接；REST 用机器 token 鉴权 |
| 内置 MCP | `crates/gonggong/src/ask.rs` 在本机回环地址提供 `gonggong`。服务端工具由 `packages/protocol/gonggong-tools.json` 生成，经 `/api/daemon/runs/:runId/tools/:name` 转发（见《内置MCP-聊天记录与群信息-开发计划》C5–C7） |
| 权限 | `gonggong` 下的工具全部自动放行（同上 C10） |
| 会话 | 主站 cookie `httpOnly`、`sameSite: 'lax'`，host-only（没有 Domain 属性） |
| TLS | `GONGGONG_TLS_CERT/KEY`；`scripts/dev-cert.sh` 生成的证书覆盖 localhost 与局域网 IP |
| 进程 | agent 自己在后台起的 dev server 跟随 agent 进程，turn 结束或被打断时可能被杀，没有统一管理 |

## 2. 决策

| # | 项 | 结论 |
| --- | --- | --- |
| P1 | 分级 | L0 静态产物（HTML 附件）→ 在预览域渲染；L1 HTTP/WS 服务 → 端口隧道；L2 桌面应用 → WebRTC 推流；L3 非 HTTP 的 TCP → 不做 |
| P2 | 隧道 | 新开独立 WS `/ws/daemon/tunnel`（机器 token 鉴权），不和控制通道 `/ws/daemon` 共用，避免大流量阻塞心跳和运行事件。一个 HTTP 请求或 WS 连接对应一个 stream，二进制帧多路复用（§4） |
| P3 | 进程托管 | 由 daemon 统一托管：启动、日志、端口就绪检测、停止、空闲回收。服务的生命周期跟随工作区，不跟随 run 或 turn |
| P4 | 预览地址（生产） | 泛域名 `https://<slug>.<GONGGONG_PREVIEW_DOMAIN>`，由 server 按 Host 分流。**预览域必须用独立的可注册域名**（例如主站 `gg.example.com`，预览 `example-preview.com`），与主站不同站，否则主站 cookie 会被同站请求带上，产生 CSRF 风险 |
| P5 | 预览地址（开发 / 局域网） | 不配 `GONGGONG_PREVIEW_DOMAIN` 时用**端口模式**：server 从 `GONGGONG_PREVIEW_PORTS`（默认 `41000-41099`）按需分配端口，地址为 `https://<主站 host>:<port>`，复用开发证书（已覆盖局域网 IP），局域网内直接可用，不依赖外网 DNS。不同端口是不同源，localStorage 等隔离成立；但 cookie 不区分端口，所以要靠 P6 |
| P6 | 主站 CSRF 兜底 | 主站 API 对所有非 GET 请求校验 `Origin`，必须等于主站 origin。两种模式都开启，端口模式下必需 |
| P7 | 访问鉴权 | 预览域保留路径前缀 `/__gg/`。首次访问时没有预览 cookie → 302 到主站 `/preview-auth?p=<slug>`，校验登录态和群成员身份后签发一次性 code → 回到 `/__gg/auth?code=`，在预览 host 上写入 cookie `gg_pv_<previewId>`（名字带 id，因为端口模式下多个预览共用同一个 host）。转发到 daemon 前剥掉 `gg_pv_*` cookie，不把它透传给用户服务 |
| P8 | 公开链接 | **只能由人在界面上生成**（bot 主人或群管理员），agent 不能生成。链接为 `/__gg/share/<token>`，token 只存哈希；必须设置过期时间（默认 7 天，最长由系统参数 `previewShareMaxDays` 控制）；访问计数；写审计。管理后台新增「公开链接」页，可统一查看、吊销、改过期时间。GUI 预览的公开链接只能观看 |
| P9 | 防 SSRF | daemon 只转发到 `127.0.0.1` / `::1` 上**已登记预览的端口**，其他请求直接拒绝 |
| P10 | 工具权限 | `service_start` 等于执行任意命令，**不自动放行**，按 bot 的权限策略走审批（和 agent 自己跑 Bash 同等）。`service_list/logs/stop`、`preview_*` 自动放行 |
| P11 | 上限 | 每个 bot 最多同时托管 5 个服务；每台机器隧道并发 stream 最多 64 个；预览空闲超过 `previewIdleHours`（默认 24）后关闭并停止对应服务；daemon 重启后不自动拉起服务，统一标为已退出 |
| P12 | GUI 推流 | 自建 **LiveKit**（由 server 托管为子进程，见 B1）（SFU，自带 TURN）。daemon 推一路流，SFU 分发给多个观众，内网与外网都能通。server 用 `livekit-server-sdk` 签发 token：daemon 是发布者，观众只能订阅，被授予控制权的人可以在 data channel 上发布输入事件 |
| P13 | 推流进程 | 做成独立的 sidecar 二进制 `gg-cast`（`livekit` Rust SDK + `xcap` 采集 + `enigo` 注入输入），由 daemon 按需拉起。libwebrtc 体积大、编译复杂，不塞进 `gg` 主程序；它崩溃也不影响 daemon |
| P14 | GUI 控制权 | 默认所有人只能观看。「请求控制」由 bot 主人批准，同一时刻只有一个控制者；只推该服务所属的窗口（按 pid 匹配），不推整块屏幕 |
| P15 | Linux 无头 | `service_start` 支持 `display: "virtual"`，daemon 用 Xvfb 起虚拟显示，GUI 在虚拟屏上跑，不占用机器主人的真实桌面 |

## 3. 数据模型（`src/db/schema.ts`）

| 表 | 字段 |
| --- | --- |
| `services` | id、machineId、botId、groupId、runId（发起的 run）、name、command、cwd、port?、display（`none`/`virtual`）、status（`starting`/`running`/`exited`/`failed`）、exitCode?、startedAt、exitedAt。daemon 上报状态，server 只做登记和展示 |
| `previews` | id、slug（随机，16 位 base32）、kind（`http`/`gui`/`static`）、machineId、groupId、serviceId?、attachmentId?、port?、path、title、publicPort?（端口模式下分配的端口）、createdByRunId、lastAccessAt、closedAt |
| `preview_shares` | id、previewId、tokenHash、createdBy、expiresAt、revokedAt、visitCount、lastVisitAt |

## 4. 隧道协议

帧格式：`[streamId u32][type u8][payload]`，type 取以下几种：

| type | 方向 | payload |
| --- | --- | --- |
| `open` | s→d | JSON `{ previewId, port, method, path, headers, upgrade }` |
| `head` | d→s | JSON `{ status, headers }` |
| `data` | 双向 | 请求体或响应体字节；升级（101）之后为连接上的原始字节，WebSocket 帧原样透传 |
| `end` | 双向 | 空，表示本方向结束 |
| `reset` | 双向 | JSON `{ reason }` |

- JSON 部分用 zod 定义在 `packages/protocol/src/tunnel.ts`，fixtures 放 `fixtures/tunnel.*.json`，Rust 在 `protocol.rs` 同步。二进制头的编解码两端各自实现，用同一组十六进制样例测往返。
- 背压：服务端写帧时等 `ws.send` 回调，daemon 侧出站队列有上限（256 帧），不自己做窗口。
- Host 头改写成 `127.0.0.1:<port>`，并补上 `X-Forwarded-Host/Proto`，因为 vite 等 dev server 默认会校验 Host。

## 5. MCP 工具（追加到内置 `gonggong`）

| 工具 | 入参 | 行为 |
| --- | --- | --- |
| `service_start` | `name`、`command`、`cwd?`（工作区相对路径）、`port?`、`env?`、`display?` | daemon 在工作区里托管进程；给了 `port` 就等待端口就绪（最多 60s），返回状态和最后 50 行日志 |
| `service_list` | — | 本 bot 的服务：名字、状态、端口、运行时长、关联的预览 |
| `service_logs` | `name`、`tail?`（默认 100，最大 1000） | 日志尾部（环形缓冲，同时落盘到 `.gonggong/services/<name>.log`） |
| `service_stop` | `name` | 停止整个进程组，关闭关联的预览 |
| `preview_expose` | `port` 或 `service`，`title`，`path?` | 登记 HTTP 预览，在群里发一张预览卡片，返回 URL |
| `preview_static` | `dir?`（工作区内目录）、`title`、`path?` | daemon 在进程内把该目录作为静态站点托管（记为服务 `static-<dir>`），再按端口转发 `preview_expose`（L0） |
| `preview_gui` | `service`、`title` | 拉起 `gg-cast` 推送该服务的窗口，发一张 GUI 卡片 |
| `preview_close` | `preview` | 关闭预览（服务保留） |

系统提示词加一句：「需要给群里看运行中的网页或应用时，用 service_start 启动、preview_expose 发布，不要自己在后台起进程。」

## 6. 界面（按 macOS 27 设计系统）

- **预览卡片**（新的消息内容块 `preview`）：标题、状态点（运行中 / 离线 / 已关闭）、可展开的内嵌 iframe（GUI 卡片展开后是视频画面）、打开、复制链接、二维码；「生成公开链接」只对 bot 主人和群管理员显示。
- **群侧边栏「预览」**：当前群所有预览和服务，可停止、查看日志。
- **管理后台「公开链接」**：全站列表（预览、群、创建人、过期时间、访问次数、最近访问），支持吊销和修改过期时间。
- **GUI 观看页**：`livekit-client` 订阅视频；控制者的鼠标和键盘事件经 data channel 发出；顶栏显示当前控制者和「请求控制 / 交还」。

## 8. 风险与待验证

1. **B0 的结论决定里程碑 B 是否按此推进**：libwebrtc 的跨平台编译、按窗口采集的可靠性（Wayland 限制多）、macOS 的 TCC 权限体验。
2. 端口模式靠 P6 兜底；生产环境一定要用独立的预览域名（P4），部署文档里要写清楚。
3. 隧道流量全部经 server 中继，团队规模大时要看带宽。先在 `机器与网络` 页上展示每台机器的隧道流量，暂不做限速。
4. 公开链接等于把 daemon 本机的服务暴露到公网，所以：必须设置过期、默认 7 天、可以一键吊销、全程审计。

## 9. 不做

- 非 HTTP 的 TCP 转发（数据库、gRPC 等）。
- 整屏共享、macOS 上的多窗口合成。
- 服务在 daemon 重启后自动恢复。

## 10. 实施记录（2026-09-27）

A1–A10 已完成，各切片测试全绿，typecheck、lint 通过；e2e `e2e/previews.spec.ts` 使用 mock agent，覆盖启动服务、发布、打开、内嵌静态站点和从侧边栏关闭。实现中相对上文的调整：

| 项 | 调整 | 原因 |
| --- | --- | --- |
| 升级连接 | 101 之后透传原始字节，不再按 opcode 拆分 WS 消息 | 更简单，也能支持任意 Upgrade 协议 |
| L0 静态预览 | 由附件改为 `preview_static`：daemon 在进程内托管工作区目录，走同一条隧道 | agent 产出的报告和构建产物往往是多文件；桌面端在进程内运行 daemon，无法依赖另起的 `gg` 子进程 |
| hello | 新增 `services` 快照，服务端据此把已丢失的服务标为已退出 | 断线重连后服务仍在，daemon 重启后服务不在，只靠 online 事件无法区分 |
| `previews.sync` | 连接时只在有打开的预览时发送；预览变化时照常发送 | 新 daemon 的白名单本来就是空的，服务端也不会为已关闭的预览开流 |
| 预览 cookie | https 下为 `SameSite=None; Secure; Partitioned`，http 开发环境为 `Lax` | 域名模式下内嵌在聊天里的预览属于第三方 iframe |
| 卡片消息 | bot 消息只带 `meta.preview`，不带 `runId` | 带 `runId` 会被引用和 `get_run` 误当成本轮最终回复 |
| 服务关联 | 收到 `service.state` 时，把同一 (群, bot, 端口) 下未关联服务的预览补上关联 | `preview_static` 是按端口发布的，发布时服务端可能还没收到服务状态 |
| 进程清理 | `gg run` 收到 SIGTERM/Ctrl-C 时停掉全部托管服务；桌面端解绑时立即结束；端口已被占用时拒绝启动 | e2e 暴露了 daemon 被结束后进程残留、以及端口就绪误判的问题 |
| 审计 | 新增分类 `preview`：生成、收回、延期、通过公开链接访问 | 管理后台可按「预览」筛选 |
| 系统参数 | `previewIdleHours`（默认 24）、`previewShareMaxDays`（默认 30） | P8、P11 |
| 部署变量 | `GONGGONG_PREVIEW_DOMAIN`（域名模式）、`GONGGONG_PREVIEW_PORTS`（端口模式范围）、`GONGGONG_PUBLIC_URL`（主站地址，把未登录的访客送回主站）、`GONGGONG_PREVIEW_HOST`（端口模式监听地址，局域网设为 `0.0.0.0`） | 局域网开发时主服务器只监听本机，预览端口需要单独开放 |

未做：卡片二维码；侧边栏查看服务日志（目前只提供给 agent 的 `service_logs`）。里程碑 B（桌面应用推流）尚未开始，先做 B0 技术验证。

## 11. B0 技术验证结论（2026-09-28，macOS 26 · Apple Silicon）

验证程序在 `crates/gg-cast`（独立 workspace，不参与主构建）：`spike/clock.py` 是毫秒时钟窗口，`spike/viewer.html` 是观看页。本机 `livekit-server --dev`（1.13.7），浏览器 Chrome。延迟的测法是：在同一张截图里，把观看页上的本机时钟和视频里的时钟相减。

| 指标 | 结果 |
| --- | --- |
| 按 pid 找窗口 | 通过：xcap 按 pid 找到窗口，其 id 与 SDK 自带采集器（ScreenCaptureKit）的 `CaptureSource::id()` 一致 |
| 端到端延迟 | 小窗口 35–47 ms，大窗口（2880×1776 像素）约 54 ms（本机回环，不含公网） |
| 帧率 / 丢帧 | 28 fps，0 丢帧，抖动缓冲 5–12 ms |
| CPU（大窗口） | native 采集 + **H264 约 8%**（硬件编码）；native + VP8 约 32%；xcap 截图 + VP8 约 41% |
| 内存 | H264 65 MB，VP8 约 230–290 MB |
| 码率 | 画面基本静止时约 300 kbps（上限设为 3 Mbps） |
| 多人观看 | 3 个观众时推流端 CPU 不变（8.1%）：由 SFU 分发，推流端只上传一路 |
| 连接房间 | 约 170 ms |
| 二进制体积 | release 29 MB，strip 后 22 MB（`gg` 主程序不受影响） |
| 远程点击 | 数据通道 → enigo 注入可行，坐标系为 point（与 xcap 一致）；注入的是可信事件（页面收到 `isTrusted`） |

实测中发现、并需要带进正式实现的点：

1. **编码默认用 H264**：macOS 上 CPU 只有 VP8 的约四分之一；浏览器解码不支持时回退 VP8。
2. **采集用 SDK 自带的 native 采集器**，xcap 只用来按 pid 找窗口 id；按 xcap 截图的方式更慢、更占内存。
3. **enigo 移动鼠标后要等约 20 ms 再点击**，否则 macOS 仍会把点击发到旧的光标位置。
4. **点击后台应用前要先把它切到前台**，否则第一次点击只起激活作用。验证里用 osascript 实现，耗时 170–360 ms；正式实现改用 `NSRunningApplication activate`。
5. **链接参数 `-ObjC`**（`build.rs`），否则 libwebrtc 运行时会报 unrecognized selector。
6. **权限**：屏幕录制和辅助功能权限都归属于启动 gg-cast 的宿主应用（终端或桌面端），`gg diag` 要能检查并提示。
7. 测试用的 miniconda Tk 窗口不响应合成点击（直接调用 CoreGraphics 注入也一样），而 Chrome 能正常收到，这是 Tk 自身的限制。e2e 的目标应用改用 Electron 或 WebView。

未验证：Windows、Linux（Xvfb）只保证后续能编译通过，实测等有机器或 CI 时再补；公网和 TURN 环境下的延迟也未测。

结论：**达标，里程碑 B 按 P12–P15 推进**，并吸收上面 7 点。
