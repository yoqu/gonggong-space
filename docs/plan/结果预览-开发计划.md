# 结果预览开发计划：服务托管、端口隧道与桌面应用推流

目标：agent 在 daemon 本机做出的结果（网页、端口服务、桌面应用），群成员能在聊天里直接看、直接用，也可以生成外部公开链接。不引入 frp 这类独立的穿透组件，复用 daemon 和 server 之间已有的长连接。

## 1. 现状

| 项 | 现状 |
| --- | --- |
| daemon 连接 | daemon 主动连 `/ws/daemon`（`apps/server/src/daemon/gateway.ts`、`hub.ts`），按 machineId 维护单连接；REST 用机器 token 鉴权 |
| 内置 MCP | `crates/gonggong/src/ask.rs` 在本机回环地址提供 `gonggong`。服务端工具由 `packages/protocol/gonggong-tools.json` 生成，经 `/api/daemon/runs/:runId/tools/:name` 转发（见《内置MCP-聊天记录与群信息-开发计划》C5–C7） |
| 权限 | `gonggong` 下的工具全部自动放行（同上 C10） |
| 会话 | 主站 cookie `httpOnly`、`sameSite: 'lax'`，host-only（没有 Domain 属性） |
| TLS | `GONGGONG_TLS_CERT/KEY`；`scripts/dev-cert.sh` 生成的证书覆盖 localhost 与局域网 IP |
| 进程 | agent 自己在后台起的 dev server 跟随 agent 进程，turn 结束或被打断时可能被杀，没有统一管理 |

## 2. 决策

| # | 项 | 结论 |
| --- | --- | --- |
| P1 | 分级 | L0 静态产物（HTML 附件）→ 在预览域渲染；L1 HTTP/WS 服务 → 端口隧道；L2 桌面应用 → WebRTC 推流；L3 非 HTTP 的 TCP → 不做 |
| P2 | 隧道 | 新开独立 WS `/ws/daemon/tunnel`（机器 token 鉴权），不和控制通道 `/ws/daemon` 共用，避免大流量阻塞心跳和运行事件。一个 HTTP 请求或 WS 连接对应一个 stream，二进制帧多路复用（§4） |
| P3 | 进程托管 | 由 daemon 统一托管：启动、日志、端口就绪检测、停止、空闲回收。服务的生命周期跟随工作区，不跟随 run 或 turn |
| P4 | 预览地址（生产） | 泛域名 `https://<slug>.<GONGGONG_PREVIEW_DOMAIN>`，由 server 按 Host 分流。**预览域必须用独立的可注册域名**（例如主站 `gg.example.com`，预览 `example-preview.com`），与主站不同站，否则主站 cookie 会被同站请求带上，产生 CSRF 风险 |
| P5 | 预览地址（开发 / 局域网） | 不配 `GONGGONG_PREVIEW_DOMAIN` 时用**端口模式**：server 从 `GONGGONG_PREVIEW_PORTS`（默认 `41000-41099`）按需分配端口，地址为 `https://<主站 host>:<port>`，复用开发证书（已覆盖局域网 IP），局域网内直接可用，不依赖外网 DNS。不同端口是不同源，localStorage 等隔离成立；但 cookie 不区分端口，所以要靠 P6 |
| P6 | 主站 CSRF 兜底 | 主站 API 对所有非 GET 请求校验 `Origin`，必须等于主站 origin。两种模式都开启，端口模式下必需 |
| P7 | 访问鉴权 | 预览域保留路径前缀 `/__gg/`。首次访问时没有预览 cookie → 302 到主站 `/preview-auth?p=<slug>`，校验登录态和群成员身份后签发一次性 code → 回到 `/__gg/auth?code=`，在预览 host 上写入 cookie `gg_pv_<previewId>`（名字带 id，因为端口模式下多个预览共用同一个 host）。转发到 daemon 前剥掉 `gg_pv_*` cookie，不把它透传给用户服务 |
| P8 | 公开链接 | **只能由人在界面上生成**（bot 主人或群管理员），agent 不能生成。链接为 `/__gg/share/<token>`，token 只存哈希；必须设置过期时间（默认 7 天，最长由系统参数 `previewShareMaxDays` 控制）；访问计数；写审计。管理后台新增「公开链接」页，可统一查看、吊销、改过期时间。GUI 预览的公开链接只能观看 |
| P9 | 防 SSRF | daemon 只转发到 `127.0.0.1` / `::1` 上**已登记预览的端口**，其他请求直接拒绝 |
| P10 | 工具权限 | `service_start` 等于执行任意命令，**不自动放行**，按 bot 的权限策略走审批（和 agent 自己跑 Bash 同等）。`service_list/logs/stop`、`preview_*` 自动放行 |
| P11 | 上限 | 每个 bot 最多同时托管 5 个服务；每台机器隧道并发 stream 最多 64 个；预览空闲超过 `previewIdleHours`（默认 24）后关闭并停止对应服务；daemon 重启后不自动拉起服务，统一标为已退出 |
| P12 | GUI 推流 | 自建 **LiveKit**（由 server 托管为子进程，见 B1）（SFU，自带 TURN）。daemon 推一路流，SFU 分发给多个观众，内网与外网都能通。server 用 `livekit-server-sdk` 签发 token：daemon 是发布者，观众只能订阅，被授予控制权的人可以在 data channel 上发布输入事件 |
| P13 | 推流进程 | 做成独立的 sidecar 二进制 `gg-cast`（`livekit` Rust SDK + `xcap` 采集 + `enigo` 注入输入），由 daemon 按需拉起。libwebrtc 体积大、编译复杂，不塞进 `gg` 主程序；它崩溃也不影响 daemon |
| P14 | GUI 控制权 | 默认所有人只能观看。「请求控制」由 bot 主人批准，同一时刻只有一个控制者；只推该服务所属的窗口（按 pid 匹配），不推整块屏幕 |
| P15 | Linux 无头 | `service_start` 支持 `display: "virtual"`，daemon 用 Xvfb 起虚拟显示，GUI 在虚拟屏上跑，不占用机器主人的真实桌面 |

## 3. 数据模型（`src/db/schema.ts`）

| 表 | 字段 |
| --- | --- |
| `services` | id、machineId、botId、groupId、runId（发起的 run）、name、command、cwd、port?、display（`none`/`virtual`）、status（`starting`/`running`/`exited`/`failed`）、exitCode?、startedAt、exitedAt。daemon 上报状态，server 只做登记和展示 |
| `previews` | id、slug（随机，16 位 base32）、kind（`http`/`gui`/`static`）、machineId、groupId、serviceId?、attachmentId?、port?、path、title、publicPort?（端口模式下分配的端口）、createdByRunId、lastAccessAt、closedAt |
| `preview_shares` | id、previewId、tokenHash、createdBy、expiresAt、revokedAt、visitCount、lastVisitAt |

## 4. 隧道协议

帧格式：`[streamId u32][type u8][payload]`，type 取以下几种：

| type | 方向 | payload |
| --- | --- | --- |
| `open` | s→d | JSON `{ previewId, port, method, path, headers, upgrade }` |
| `head` | d→s | JSON `{ status, headers }` |
| `data` | 双向 | 请求体或响应体字节；升级（101）之后为连接上的原始字节，WebSocket 帧原样透传 |
| `end` | 双向 | 空，表示本方向结束 |
| `reset` | 双向 | JSON `{ reason }` |

- JSON 部分用 zod 定义在 `packages/protocol/src/tunnel.ts`，fixtures 放 `fixtures/tunnel.*.json`，Rust 在 `protocol.rs` 同步。二进制头的编解码两端各自实现，用同一组十六进制样例测往返。
- 背压：服务端写帧时等 `ws.send` 回调，daemon 侧出站队列有上限（256 帧），不自己做窗口。
- Host 头改写成 `127.0.0.1:<port>`，并补上 `X-Forwarded-Host/Proto`，因为 vite 等 dev server 默认会校验 Host。

## 5. MCP 工具（追加到内置 `gonggong`）

| 工具 | 入参 | 行为 |
| --- | --- | --- |
| `service_start` | `name`、`command`、`cwd?`（工作区相对路径）、`port?`、`env?`、`display?` | daemon 在工作区里托管进程；给了 `port` 就等待端口就绪（最多 60s），返回状态和最后 50 行日志 |
| `service_list` | — | 本 bot 的服务：名字、状态、端口、运行时长、关联的预览 |
| `service_logs` | `name`、`tail?`（默认 100，最大 1000） | 日志尾部（环形缓冲，同时落盘到 `.gonggong/services/<name>.log`） |
| `service_stop` | `name` | 停止整个进程组，关闭关联的预览 |
| `preview_expose` | `port` 或 `service`，`title`，`path?` | 登记 HTTP 预览，在群里发一张预览卡片，返回 URL |
| `preview_static` | `dir?`（工作区内目录）、`title`、`path?` | daemon 在进程内把该目录作为静态站点托管（记为服务 `static-<dir>`），再按端口转发 `preview_expose`（L0） |
| `preview_gui` | `service`、`title` | 拉起 `gg-cast` 推送该服务的窗口，发一张 GUI 卡片 |
| `preview_close` | `preview` | 关闭预览（服务保留） |

系统提示词加一句：「需要给群里看运行中的网页或应用时，用 service_start 启动、preview_expose 发布，不要自己在后台起进程。」

## 6. 界面（按 macOS 27 设计系统）

- **预览卡片**（新的消息内容块 `preview`）：标题、状态点（运行中 / 离线 / 已关闭）、可展开的内嵌 iframe（GUI 卡片展开后是视频画面）、打开、复制链接、二维码；「生成公开链接」只对 bot 主人和群管理员显示。
- **群侧边栏「预览」**：当前群所有预览和服务，可停止、查看日志。
- **管理后台「公开链接」**：全站列表（预览、群、创建人、过期时间、访问次数、最近访问），支持吊销和修改过期时间。
- **GUI 观看页**：`livekit-client` 订阅视频；控制者的鼠标和键盘事件经 data channel 发出；顶栏显示当前控制者和「请求控制 / 交还」。

## 8. 风险与待验证

1. **B0 的结论决定里程碑 B 是否按此推进**：libwebrtc 的跨平台编译、按窗口采集的可靠性（Wayland 限制多）、macOS 的 TCC 权限体验。
2. 端口模式靠 P6 兜底；生产环境一定要用独立的预览域名（P4），部署文档里要写清楚。
3. 隧道流量全部经 server 中继，团队规模大时要看带宽。先在 `机器与网络` 页上展示每台机器的隧道流量，暂不做限速。
4. 公开链接等于把 daemon 本机的服务暴露到公网，所以：必须设置过期、默认 7 天、可以一键吊销、全程审计。

## 9. 不做

- 非 HTTP 的 TCP 转发（数据库、gRPC 等）。
- 整屏共享、macOS 上的多窗口合成。
- 服务在 daemon 重启后自动恢复。

## 10. 实施记录（2026-09-27）

A1–A10 已完成，各切片测试全绿，typecheck、lint 通过；e2e `e2e/previews.spec.ts` 使用 mock agent，覆盖启动服务、发布、打开、内嵌静态站点和从侧边栏关闭。实现中相对上文的调整：

| 项 | 调整 | 原因 |
| --- | --- | --- |
| 升级连接 | 101 之后透传原始字节，不再按 opcode 拆分 WS 消息 | 更简单，也能支持任意 Upgrade 协议 |
| L0 静态预览 | 由附件改为 `preview_static`：daemon 在进程内托管工作区目录，走同一条隧道 | agent 产出的报告和构建产物往往是多文件；桌面端在进程内运行 daemon，无法依赖另起的 `gg` 子进程 |
| hello | 新增 `services` 快照，服务端据此把已丢失的服务标为已退出 | 断线重连后服务仍在，daemon 重启后服务不在，只靠 online 事件无法区分 |
| `previews.sync` | 连接时只在有打开的预览时发送；预览变化时照常发送 | 新 daemon 的白名单本来就是空的，服务端也不会为已关闭的预览开流 |
| 预览 cookie | https 下为 `SameSite=None; Secure; Partitioned`，http 开发环境为 `Lax` | 域名模式下内嵌在聊天里的预览属于第三方 iframe |
| 卡片消息 | bot 消息只带 `meta.preview`，不带 `runId` | 带 `runId` 会被引用和 `get_run` 误当成本轮最终回复 |
| 服务关联 | 收到 `service.state` 时，把同一 (群, bot, 端口) 下未关联服务的预览补上关联 | `preview_static` 是按端口发布的，发布时服务端可能还没收到服务状态 |
| 进程清理 | `gg run` 收到 SIGTERM/Ctrl-C 时停掉全部托管服务；桌面端解绑时立即结束；端口已被占用时拒绝启动 | e2e 暴露了 daemon 被结束后进程残留、以及端口就绪误判的问题 |
| 审计 | 新增分类 `preview`：生成、收回、延期、通过公开链接访问 | 管理后台可按「预览」筛选 |
| 系统参数 | `previewIdleHours`（默认 24）、`previewShareMaxDays`（默认 30） | P8、P11 |
| 部署变量 | `GONGGONG_PREVIEW_DOMAIN`（域名模式）、`GONGGONG_PREVIEW_PORTS`（端口模式范围）、`GONGGONG_PUBLIC_URL`（主站地址，把未登录的访客送回主站）、`GONGGONG_PREVIEW_HOST`（端口模式监听地址，局域网设为 `0.0.0.0`） | 局域网开发时主服务器只监听本机，预览端口需要单独开放 |

未做：卡片二维码；侧边栏查看服务日志（目前只提供给 agent 的 `service_logs`）。里程碑 B（桌面应用推流）尚未开始，先做 B0 技术验证。

## 11. B0 技术验证结论（2026-09-28，macOS 26 · Apple Silicon）

验证程序在 `crates/gg-cast`（独立 workspace，不参与主构建）：`spike/clock.py` 是毫秒时钟窗口，`spike/viewer.html` 是观看页。本机 `livekit-server --dev`（1.13.7），浏览器 Chrome。延迟的测法是：在同一张截图里，把观看页上的本机时钟和视频里的时钟相减。

| 指标 | 结果 |
| --- | --- |
| 按 pid 找窗口 | 通过：xcap 按 pid 找到窗口，其 id 与 SDK 自带采集器（ScreenCaptureKit）的 `CaptureSource::id()` 一致 |
| 端到端延迟 | 小窗口 35–47 ms，大窗口（2880×1776 像素）约 54 ms（本机回环，不含公网） |
| 帧率 / 丢帧 | 28 fps，0 丢帧，抖动缓冲 5–12 ms |
| CPU（大窗口） | native 采集 + **H264 约 8%**（硬件编码）；native + VP8 约 32%；xcap 截图 + VP8 约 41% |
| 内存 | H264 65 MB，VP8 约 230–290 MB |
| 码率 | 画面基本静止时约 300 kbps（上限设为 3 Mbps） |
| 多人观看 | 3 个观众时推流端 CPU 不变（8.1%）：由 SFU 分发，推流端只上传一路 |
| 连接房间 | 约 170 ms |
| 二进制体积 | release 29 MB，strip 后 22 MB（`gg` 主程序不受影响） |
| 远程点击 | 数据通道 → enigo 注入可行，坐标系为 point（与 xcap 一致）；注入的是可信事件（页面收到 `isTrusted`） |

实测中发现、并需要带进正式实现的点：

1. **编码默认用 H264**：macOS 上 CPU 只有 VP8 的约四分之一；浏览器解码不支持时回退 VP8。
2. **采集用 SDK 自带的 native 采集器**，xcap 只用来按 pid 找窗口 id；按 xcap 截图的方式更慢、更占内存。
3. **enigo 移动鼠标后要等约 20 ms 再点击**，否则 macOS 仍会把点击发到旧的光标位置。
4. **点击后台应用前要先把它切到前台**，否则第一次点击只起激活作用。验证里用 osascript 实现，耗时 170–360 ms；正式实现改用 `NSRunningApplication activate`。
5. **链接参数 `-ObjC`**（`build.rs`），否则 libwebrtc 运行时会报 unrecognized selector。
6. **权限**：屏幕录制和辅助功能权限都归属于启动 gg-cast 的宿主应用（终端或桌面端），`gg diag` 要能检查并提示。
7. 测试用的 miniconda Tk 窗口不响应合成点击（直接调用 CoreGraphics 注入也一样），而 Chrome 能正常收到，这是 Tk 自身的限制。e2e 的目标应用改用 Electron 或 WebView。

未验证：Windows、Linux（Xvfb）只保证后续能编译通过，实测等有机器或 CI 时再补；公网和 TURN 环境下的延迟也未测。

结论：**达标，里程碑 B 按 P12–P15 推进**，并吸收上面 7 点。

## 12. 微信小程序技术验证结论（2026-09-28，macOS 26 · 微信开发者工具 2.01.2510290）

小程序不是 HTTP 服务，走不了 L1 隧道，因此归入 L2：用开发者工具的模拟器充当「窗口」，gg-cast 负责推流；再加上开发者工具自带的自动化通道，用来打开指定页面。验证用的是一个自建 demo，以及本机真实业务项目（`luke-plus-miniprogram`，带分包和 tabBar）。

| 指标 | 结果 |
| --- | --- |
| 开启自动化 | `cli auto --project <dir> --auto-port <port> --trust-project`（`--auto-port` 是 help 里隐藏的参数）。IDE 已登录时 3–4 s 完成，端口在编译完成后约 5 s 内开始监听 |
| 打开指定页面 | 在自动化 WS 上发 `App.callWxMethod {method: reLaunch/navigateTo/switchTab, args:[{url}]}`，0.6–2.4 s 返回；`App.getCurrentPage` 能拿到 path 和 query |
| 读数据、定位元素 | `App.callFunction` 在逻辑层执行函数：`getCurrentPages()` 读页面 data，`wx.createSelectorQuery` 取元素坐标，5–60 ms |
| 内容截图 | `App.captureScreenshot` 返回 PNG base64，只含页面内容（不含导航栏），简单页 40–85 ms，业务页约 210 ms；可用来做卡片首屏截图 |
| 推流 | 模拟器独立窗口 390×930 pt；xcap 采集 + H264，28 fps，采集约 25 ms/帧，推流端 CPU 6–8%、内存约 32 MB；滚动时码率峰值约 4 Mbps，静止时约 110 kbps，0 丢帧 |
| 操作往返（观看端点击 → 看到画面变化） | 中位数 105 ms（79–128 ms），注入本身约 22 ms；首次约 475 ms |
| 输入 | 点击（坐标与页面 css px 1:1）、拖动滚动（带惯性）、键盘输入（含中文，走 unicode 字符串，不经过输入法）都能生效；点击置顶窗口时应用会自动切到前台，所以无需额外激活 |
| 多项目 | 两个项目的自动化端口可以同时存在；按决策仍限制单实例（两个置顶窗口会互相遮挡） |

发现的问题，以及需要带进 B6 的做法：

1. **被遮挡的窗口会停止渲染**（Chromium 遮挡检测）：画面冻结，`captureScreenshot` 和 `reLaunch` 会一直挂起。解决办法：把模拟器切成**独立窗口并置顶**，两步都用辅助功能 API 完成（开启 `AXManualAccessibility` 后按描述找到「分离窗口」和「置顶窗口」并 `AXPress`，约 20–45 ms，不用移动鼠标）。整套准备约 1.8 s。
2. **`cli auto` 每次都会重建会话**，模拟器回到嵌入模式，之前的独立窗口变成不再更新的僵尸窗口，而且会挡住新窗口。顺序固定为：先关闭旧的模拟器窗口（AX 关闭按钮）→ `cli auto` → 分离 → 置顶。
3. **独立模拟器窗口会让自动化会话一直存活**：`cli close` 之后端口仍在，要先关掉模拟器窗口。收尾顺序：关闭模拟器窗口 → `cli close --project` → 等端口释放 → 需要时再 `cli open` 恢复用户原来的状态（紧接着 `open` 会和关闭窗口撞车，窗口不显示）。
4. **自动化端口监听在所有网卡上（`*:<port>`）且没有鉴权**，已在局域网 IP 上实测连通。任何人都能用 `App.callFunction` 在小程序里执行任意代码。只在预览期间开启，端口随机，预览结束立即按第 3 点关闭；`gg diag` 提示机器主人开启系统防火墙。
5. **native 采集器看不到置顶窗口**：libwebrtc 的窗口列表会过滤 layer≠0 的窗口，所以小程序必须用 xcap 采集。窗口小，开销可以接受；按窗口标题「<项目名>的模拟器」匹配（开发者工具的所有窗口同属一个 pid）。
6. **游客 appid（`touristappid`）无法开启自动化**，必须使用真实 appid，IDE 也要保持登录：用 `GET /v2/islogin` 检测（HTTP 端口记录在用户目录的 `.ide` 文件里），过期时用 `cli login -f base64` 生成登录二维码转给机器主人。IDE 的「安全设置 → 服务端口」必须打开。
7. **不要依赖 `miniprogram-automator` SDK**：它的 `reLaunch` 在当前版本会挂起，而且 `Page.*` / `Element.*` 渲染层命令在基础库 3.x 下全部超时。daemon 直接用 Rust 发 WS JSON（`{id, method, params}`），只用 `App.*` 和 `Tool.*`，不依赖 Node。
8. 点击会触发真实的业务逻辑（实测点击 tab 弹出了订阅消息授权框），这属于正常行为，靠控制权审批来约束。

未验证：Windows（AX 相关步骤要换成 UI Automation），以及 `cli preview` 真机扫码（会把代码上传到微信服务器，没有在业务 appid 上试）。

结论：**方案可行，B6 按「自动化打开页面 + 独立置顶模拟器 + gg-cast(xcap) 推流 + enigo 注入」推进**，并吸收上面 8 点。截图轮询（约 5–20 fps，而且照样需要窗口可见）只用于卡片首屏截图，不作为实时画面方案。

### 12.1 不置顶方案：参考 Codex Computer Use（2026-09-28 补充验证）

Codex 的 Computer Use（源自 Sky，开源复刻见 trycua/cua 的 cua-driver）靠三件事在后台操作应用，不抢焦点：用 AX 树按元素执行 `AXPress`；用 SkyLight 私有 API `SLEventPostToPid` 把事件直接投递给目标进程，事件带上窗口号等字段，并先发一次 (-1,-1) 诱饵点击以满足 Chromium 的用户激活检查；用 yabai 的 focus-without-raise（`SLPSPostEventRecordTo`）让目标在输入路由上变成活动应用，但窗口不前置。采集用 ScreenCaptureKit 按窗口截取，被遮挡的窗口也能截。

对开发者工具的实测结果：

| 项目 | 结果 |
| --- | --- |
| 被遮挡时 SCK 持续采集 | **不能恢复渲染**。逻辑层照常跳转，渲染层冻结，`captureScreenshot` 挂起。Codex/cua 方案没有解决 Chromium 遮挡检测的问题 |
| 窗口停靠在屏幕边缘（只露 2–3 pt，用 AX 设置位置） | 渲染正常；被其他窗口盖住大部分时也不受影响；SCK 能采集到完整窗口（包括屏幕外部分） |
| 后台点击（SkyLight 方案，坐标在屏幕外） | 生效，鼠标不动，前台应用不变 |
| 后台键盘（`CGEvent.postToPid`，含中文） | 生效，前台应用不变 |
| 后台拖动或滚轮 | **不生效**（与 cua 文档说的「部分后台 scroll/drag 会被拒绝」一致） |

补充测试（拖动、滚动、可靠性）：

| 项目 | 结果 |
| --- | --- |
| 后台拖动（5 种构造：纯 SkyLight、加 focus-without-raise、加 (-1,-1) 诱饵、NSEvent 带窗口内坐标、按 cua 构造） | touchstart/touchend 能到，**touchmove 始终为 0**：拖动过程中的移动事件被 Chromium 丢弃，拖不动 |
| 后台滚动 | 滚轮无效；**先点击滚动区域，再发方向键（`postToPid`）可以滚动**（8 次 ↓ ≈ 160–200 px），只能竖向、步进粗糙 |
| 后台点击成功率（每轮 10 次，用户在使用电脑时） | 不激活 40–100%，带激活 40–90%；失败表现为事件整次丢失，或者丢了抬起之后连续几次都没反应。换事件源（nil/combined/private）、把按下到抬起的间隔拉长到 40 ms 都没有改善 |
| focus-without-raise 的副作用 | 用户前台窗口会失去 key 状态（按键仍能收到，但窗口显示为非激活）。SLPS 焦点记录、AX 设置主窗口、`activate`、`SLPSSetFrontProcessWithOptions` 四种方法都没能恢复。不激活的点击没有这个副作用 |

结论：SkyLight 后台输入**不够可靠**，只适合「尽力而为」的 agent 操作（配合结果校验、失败重试），不适合给人实时远程操控，而且拖动和滑动类手势都做不了。B6 仍然采用「独立窗口 + 置顶 + HID 注入」（§12 实测零失败）。边缘停靠可以保证渲染不冻结，适合「只看不控」的观看模式：观看者只看画面时停在边缘，拿到控制权后再移回屏幕内并置顶。另一个没验证的路线是由 daemon 带 `--remote-debugging-port --disable-backgrounding-occluded-windows` 启动 IDE，再用 CDP `Input.dispatchTouchEvent`：这样既能全后台，又不需要私有 API，但需要接管 IDE 的启动过程（用户已经打开的 IDE 必须重启）。

### 12.2 新版开发者工具（2.02.2608070，Electron 内核）重新验证（2026-09-28）

开发者工具在验证期间自动升级为 Electron 版（Electron 36 / Chrome 136），§12、§12.1 里 NW.js 版的不少限制已经不存在：

| 项目 | 结果 |
| --- | --- |
| 官方 agent CLI `wechatide`（skill v0.3.9） | 自带 `open_project_window`（默认 liteMode，窗口里只有模拟器）、`automation_navigate`、`simulator_screenshot`、`automation_element_action`（按 selector 点击、输入、滚动）、`automation_viewport_action pageScrollTo`、`get_simulator_console/network`、`create_preview_qrcode`。每次调用约 1 s（含 CLI 进程启动）。前提是「设置 → 安全 → 服务端口」已开启（升级后换了新的配置目录，这一项默认关闭），并且在 IDE 弹窗里授权了 clientName；可以再开启 CLI 访问令牌。旧版的 `cli auto`、无鉴权 `*:port` 和 miniprogram-automator 都不需要了 |

结论与建议：

1. B6 改为基于 `wechatide`：daemon 用 `open_project_window` 打开 liteMode 窗口，窗口可以被遮挡，不用置顶；用 `automation_navigate` 打开指定页面；卡片首屏截图用 `simulator_screenshot`；agent 自己操作时用 `automation_element_action`（按 selector）；再加上 console/network 取证。daemon 可以直接连 IDE 的服务端口，不经过 CLI 进程，以减少延迟（协议待抓包确认）。

3. 人的实时操控：CDP 方案需要接管 IDE 的启动参数，而且触摸模拟的状态不稳定，暂不采用。先用「控制时把窗口切到前台 + HID 注入」（§12 已经实测稳定），把拖动这类手势留给这种模式。要做到完全后台操控，还得继续研究 IDE 自己的触摸模拟开关（它的调试器是怎么切换的）。

## 13. B6-1 小程序预览卡片（2026-09-28 开工）

范围：不依赖推流。agent 用 `preview_miniprogram` 打开项目和指定页面，群里出现一张带首屏截图的小程序卡片；在工作台里可以查看最新截图、刷新截图、切换页面。实时画面和远程操控放到 B1–B4 之后再做。

| 层 | 做法 |
| --- | --- |
| 协议 | `PreviewKind` 增加 `miniprogram`；daemon 工具 `preview_miniprogram {dir?, page?, query?, title}`（与 service_start 一样按 Bot 档位审批）；`preview_expose` 增加 `miniprogram`（机器上项目目录的绝对路径，只由 daemon 转发时填写），与 port / service 三选一；隧道 `snapshot` 目标增加 `{previewId, miniprogram}`，`path` 为 `/<page>?<query>` |
| daemon | 新增 `wechatide.rs`：扫描 `微信开发者工具/*/Default/.ide` 找端口，用心跳挑出活着的那个；作为 MCP 客户端连接（clientName `Gonggong`）。收到 401 时拉起 `wechatide auth -c Gonggong`，在机器主人那边弹出授权框，并提示 agent 稍后重试。`preview_miniprogram` 的流程：校验目录（必须有 project.config.json）→ 确保项目在运行 → 跳到目标页 → 以 `preview_expose` 转发给服务端。截图目标：当前页不是目标页时先跳页，再 `simulator_screenshot`，返回 JPEG |
| 服务端 | `previews.project` 新列；同一 (群, bot, 项目) 只保留一张打开的卡片，再次发布时更新页面并重新截图；截图按内容嗅探 png / jpeg；小程序预览不开端口监听、不能生成公开链接；截图时刷新 `lastAccessAt`；`POST /previews/:id/snapshot` 支持 `{path}`，用来切换页面 |
| 前端 | 卡片显示小程序图标、页面路径和「小程序」标记；点击后在工作台打开 `miniprogram` 标签页，显示截图，提供刷新和页面路径输入；隐藏「新窗口打开」和「公开链接」 |
| 提示词 | 「给群里看小程序时用 preview_miniprogram」 |

实施要点（2026-09-28，对真实开发者工具 2.02.2608070 实测）：

1. **跳页用 `automation_navigate reLaunch`，不用 `simulator_open_page`**：后者每次都要重新编译，而且是异步的（返回时页面还没切过去），切页要约 18 s；reLaunch 约 6 s。跳页后都要轮询 `automation_runtime_info`，等目标页真正出现再截图；刚跳页或刚打开时，截图带 `wait: 1` 等页面渲染完成。
2. **项目已经在运行时不要再调 `open_project_window`**：即使返回「复用窗口」，紧接着的 automator 调用也会慢到 10 s 以上，甚至超时。所以先查当前页，查不到才开窗口。
3. **复用一个 MCP 会话**（daemon 进程内共享，调用串行）：新会话的第一次调用约 1 s，之后每次约 0.1 s。会话失效时（IDE 重启，返回 HTTP 400）重连一次。
4. **开发者工具自己的网络抖动**：跳页时它偶尔要连微信服务器做 AppID 校验，失败时返回 `code: APPID_ERROR`（TLS 断开）或 automator 超时。对这两类最多重试 3 次，其他错误直接返回。
5. 实测耗时：打开项目并跳页约 4 s，同页刷新截图约 2.4 s，切页约 6 s。连续 17 次全部成功。
6. **「您信任此项目的作者吗？」**（2026-09-29 用户实测发现）：通过 MCP 第一次打开某个项目时，只要既没开启「设置 → 安全 → 自动化接口打开工具时默认信任项目」（`trustWhenAuto`），也没设置 CLI 访问令牌，开发者工具就会弹出信任框（逻辑见其 `ProjectManagerService.isTrustWhenAuto`）。`open_project_window` 照样很快返回成功，但之后对这个小程序的 automator 调用会一直挂住，直到有人点了按钮；MCP 和 HTTP `/open` 都不接受 `trustProject` 参数。处理方式（用户 2026-09-29 拍板「跟随 Bot 权限档位」）：`preview_miniprogram` 和 `service_start` 一样按档位审批（完全授权档自动通过，其他档由 Bot 主人远程审批），审批过的调用由 daemon 通过 macOS 辅助功能接口（`AXManualAccessibility` 打开 Electron 网页内容的辅助功能树，再 `AXPress`）按下**本项目窗口**里的「信任并运行」；窗口按 `project.config.json` / `project.private.config.json` 里 URL 编码的 `projectname` 或目录名匹配，不碰别的项目。每次查询当前页带 3 s 超时，超时视为「还没起来」并检查信任框；请求超时不再当成会话失效。实测：新项目 14.5 s 自动信任并打开，已信任项目 4.4 s。前提是运行 gg 的程序有「辅助功能」权限（`gg diag` 待补检查）；没有权限或不在 macOS 时，等满 60 s 后给出人工处理的提示。Windows 以后用 UI Automation 实现同样的操作。
7. **无人值守：自动启动与扫码登录**（2026-09-29，真实回归）：
   - daemon 连不上开发者工具时，用 `open -g -a` 在后台启动它。刚启动的 IDE 心跳已经通了，但**第一个 `initialize` 会被吞掉、永远不返回**，所以 `initialize` 只给 10 s，启动等待期（60 s）内失败就重试。
   - 未登录时走 MCP `login {type: image}`（开发者工具二维码模式的码，与面板上的「微信快捷登录」互不影响），截图返回 **202 + 二维码**。卡片进入 `awaiting = login`，二维码只对 Bot 主人和群管理员显示；服务端每 5 s 重新请求一次截图，daemon 只轮询同一个登录任务（`polling_task_result`），扫码成功后打开项目、跳页、截图，卡片自动恢复。
   - 开发者工具的两个坑：① 未登录时对小程序的查询会让它执行一次 logout，所以有待扫的码时只轮询登录任务、不再查页面，「需要重新登录」也不算网络抖动；② 新的 `login` 会作废上一个码，而且旧码到期超时的事件会把新码的任务也标记为过期（事件不区分码）。任务一旦以非成功状态结束（过期、被别处登录取消），先重新查登录状态，确实未登录才申请新码。
   - agent 的 MCP 工具调用有 60 s 超时（Claude Code / Codex）：`preview_miniprogram` 限时 45 s，超时就先发卡片，剩下的交给截图流程；截图失败原因写入 `snapshot_error` 显示在卡片上。
   - 工具说明要求 agent 不要自己用 wechatide/cli 操作开发者工具（实测 Bot 会自己发一张登录码，导致用户扫两次）。
   - 实测：二维码 11:04:20 生成，11:04:40 扫码，11:04:42 登录完成，自动信任后 11:05:11 卡片显示模拟器画面。
