# 发布与平台说明

## 产物（`bash scripts/release.sh`，输出到 `dist/<版本>/`）
| 平台 key（daemon 上报的 `<os>-<arch>`） | 文件                            | 构建方式                                                                            |
| -------------------------------- | ----------------------------- | ------------------------------------------------------------------------------- |
| macos-aarch64 / macos-x86_64     | `gonggong-<v>-macos-<arch>`       | 本机 rustup 工具链交叉编译                                                               |
| linux-x86_64 / linux-aarch64     | `gonggong-<v>-linux-<arch>`       | Docker `rust:1.98-bullseye` 交叉编译（glibc ≥ 2.31：Ubuntu 20.04+、Debian 11+、RHEL 9+） |
| windows-x86_64                   | `gonggong-<v>-windows-x86_64.exe` | 同一容器内 mingw-w64（`x86_64-pc-windows-gnu`）                                        |
| 桌面端 macOS                     | `Gonggong_<v>_<arch>.dmg`、`Gonggong_<v>_<arch>.app.tar.gz(.sig)` | `tauri build --bundles app,dmg`（`apps/desktop`），内置本机架构的 gg-cast（externalBin）；`.app.tar.gz` 是签名的应用更新包 |
| 桌面端 Windows | `Gonggong_<v>_x64-setup.exe(.sig)` | GitHub Actions `.github/workflows/desktop-windows.yml`（windows-latest，MSVC）：`tauri build --bundles nsis`，安装包本身就是签名的更新包；不内置 gg-cast |

另有 `SHA256SUMS` 与 `manifest.json`（D17：`{version, builds: {<os>-<arch>: {url, sha256}}}`），以及 GitHub 发布用的 `github/manifest.json`（同一份清单，URL 为 `https://github.com/<repo>/releases/download/v<v>/<文件>`）和 `github/latest.json`（Tauri 更新源 `{version, notes, pub_date, platforms: {darwin-<arch>: {signature, url}}}`，只含实际构建的架构；Windows 工作流再合并 `windows-x86_64`）。版本号取自 `crates/gonggong/Cargo.toml`。容器只构建 `-p gonggong`，不需要 webkit；Linux 桌面安装包暂不提供。TLS 继续用 rustls + aws-lc-rs：所有目标都用 cc 编译 aws-lc，Windows 用 `prebuilt-nasm`，不需要 cmake / nasm / clang，所以没有换成 ring。`--only macos-aarch64,desktop` 这类参数可以只构建部分产物。

## 发布
```bash
GONGGONG_DATA_DIR=<服务器数据目录> GONGGONG_ADMIN_PASSWORD=… bash scripts/release.sh --publish https://gonggong.example.com
```
脚本会把产物复制到 `$GONGGONG_DATA_DIR/downloads`（由服务器的 `GET /downloads/:file` 提供下载），再以管理员身份 `PUT /api/admin/daemon-release`。自签证书时加 `GONGGONG_CACERT=cert.pem`；产物放在 CDN 时设 `GONGGONG_DOWNLOAD_BASE=https://cdn/...`。在线的 daemon 连上后，下载与自己平台匹配的新版本并校验 sha256，没有运行中的轮次时替换自身并重启。ACP 适配器的版本锁定在 daemon 里（D19），随 daemon 一起升级。

### 管理后台上传（2026-09-29）
不方便在服务器上跑脚本时：构建机执行 `bash scripts/release.sh`（不带 `--publish`），系统管理员在「管理后台 → 客户端发布」把 `dist/<版本>/` 里的 `gonggong-*`、`gg-cast-*` 拖进去。文件名决定类型、版本与平台（`parseReleaseFile`），其他文件在浏览器端就被拒绝；服务器边接收边计算 sha256，写入 `$GONGGONG_DATA_DIR/downloads` 并更新发布记录（`POST /api/admin/daemon-release/files`，单文件上限 300 MB）。同版本按平台合并；更高版本替换整个发布并删掉旧版本在本机托管的文件；低于当前版本的拒绝。表格按平台列出 daemon / gg-cast 是否已发布及对应机器数，可逐项移除（`DELETE /api/admin/daemon-release/:kind/:platform`）。上传与移除都写审计。

## GitHub Releases 与自动更新（v0.2.0 起）

### 更新检查
- **`gg`（命令行）**：服务器发布的版本优先（D17 不变）。welcome 新增 `release` 字段——服务器有本机平台的构建时为 true，daemon 只从服务器升级；为 false（或旧服务器不带这个字段）时，daemon 连上后立即、之后每 6 小时请求 `https://api.github.com/repos/<repo>/releases/latest`（只看正式版），`tag_name` 比自己新就下载该 release 的 `manifest.json` 资产，取本平台构建，走同一套下载、sha256 校验、替换、空闲时重启。用独立 HTTP 客户端（遵循系统代理环境变量，带 User-Agent，连接 10 秒、整体 30 秒超时）；403 / 429 视为限流、等下个周期，网络失败每周期只记一行日志。`GONGGONG_UPDATE_REPO=<owner/repo>` 改仓库（默认 `yoqu/gonggong-space`），`GONGGONG_UPDATE=off` 关闭；`GONGGONG_NO_AUTO_UPGRADE=1` 或设置里关掉「自动升级」则两种来源都不升级。
- **macOS 桌面端**：Tauri 官方 updater 插件，更新源 `https://github.com/<repo>/releases/latest/download/latest.json`，用 `tauri.conf.json` 里 `plugins.updater.pubkey` 验签。启动时与每 6 小时（「自动升级」开启时）检查，后台下载，完成后右上角提示「新版本 v… 已下载，重启以更新」（立即重启 / 稍后）；「设置 → 版本」显示当前版本与状态，可手动「检查更新」。重启时先安装更新、停掉内置 daemon 及其托管服务，再重新启动；本机有运行中的任务时先确认「有运行中的任务，重启会中断」。内置 daemon 仍不自升级，随 App 更新。
- v0.1.0 的 `gg` 与桌面端都不会检查 GitHub，需要手动更新一次到 v0.2.0。

### 发布流程
1. 生成更新签名密钥（只做一次，私钥妥善保存，丢失后已安装的桌面端无法再收到更新）：
   ```bash
   pnpm --filter @gonggong/desktop tauri signer generate -w ~/.tauri/gonggong.key
   ```
   把输出的公钥（`~/.tauri/gonggong.key.pub` 的内容）填进 `apps/desktop/src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`，替换 `REPLACE_WITH_UPDATER_PUBKEY`，提交。占位符未替换或没有私钥时 `release.sh` 打桌面端会直接失败。
2. 构建并发布：
   ```bash
   export TAURI_SIGNING_PRIVATE_KEY=~/.tauri/gonggong.key     # 路径或内容
   export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=…                 # 生成时设的密码
   bash scripts/release.sh --github [--notes <文件>]
   ```
   `--github` 在构建完成后执行 `gh release create v<v> <全部产物> --title "共工空间 v<v>" --notes-file <文件>`（仓库取 `GONGGONG_GITHUB_REPO`，默认 `yoqu/gonggong-space`；说明默认 `dist/<v>/RELEASE_NOTES.md`，由 `docs/release-notes/v<v>.md` 复制而来）。上传的资产：`gonggong-*`、`gg-cast-*`、`Gonggong_*`（dmg、更新包与签名）、`SHA256SUMS`、`manifest.json`、`latest.json`。tag 不存在时 `gh` 会在默认分支最新提交上创建，先推送代码。
3. Windows 桌面端：release 发布后 `desktop-windows.yml` 自动触发，在 windows-latest 上构建 NSIS 安装包，上传 `Gonggong_<v>_x64-setup.exe` 与 `.sig`，并把 `windows-x86_64` 合并进该 release 的 `latest.json`（已安装的 Windows 桌面端据此更新）。需要先在仓库 Settings → Secrets and variables → Actions 配置与第 1 步同一把私钥：`TAURI_SIGNING_PRIVATE_KEY`（私钥文件内容）和 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。也可以在 Actions 页手动运行：填 tag（如 `v0.2.0`）就附加到该 release，不填只产出工作流构件。工作流会检查 `tauri.conf.json` 的版本与 tag 一致。
4. 自托管服务器想让成员从服务器升级，照旧 `--publish`（与 `--github` 可同时用）。

## 成员机器要求
- git；Node.js ≥ 22 和 npm（首次运行时把 ACP 适配器装到 `~/.gonggong/adapters/`）；Claude Code 和/或 Codex CLI 由成员自己安装并登录。
- Windows：用的是 `node.exe`、`claude.exe` 或 npm 生成的 `*.cmd` 启动脚本，查找路径包括 PATH、`%APPDATA%\npm` 和 `~/.local/bin`；自升级时先把正在运行的 exe 改名，再替换新文件。

## 验证方式（D16）
- **macOS**：全量 E2E 在真机上跑，沿用 M5。发布演练 `bash scripts/release/rehearse.sh` 已通过：构建全部产物 → 发布到本地服务器 → 用同一份源码打的 0.0.1 旧版 daemon 绑定后自动下载 macos-aarch64 产物，校验、替换、重启，然后以 0.1.0 上线；替换后的文件 sha256 与 manifest 一致。
- **Linux**：`bash scripts/release/cross-test.sh linux` 在 bullseye 容器里跑 `cargo test -p gonggong`，全部通过（和 macOS 的测试集相同，包括 mock agent、git、TLS）。`bash scripts/linux-e2e.sh` 已通过：服务器跑在本机（新建数据库，开发用 TLS 证书）；Linux 版 gonggong 跑在 bookworm 容器里（带 Node 22 和 mock ACP agent），用绑定码加 `--fingerprint` 经 https 绑定，证书固定生效。通过 API 触发两轮：无仓库群，回复含 `Linux` 和 Node 版本；仓库群，从 `file://` 裸仓库克隆，回复含 README 内容和提交信息。两轮状态都是 completed。容器里不跑真实 Claude Code，因为容器内没有登录。
- **Windows**（2026-10-07，Windows 11 真机）：`gg` 绑定本地 Docker 部署的服务器（https + 证书固定），`gg run` 跑通 Claude Code 一轮（写文件、回复）；Codex 经 npm 的 `.cmd` 启动、适配器初始化正常（该轮因本机第三方模型接口断连未完成）。桌面端用 GNU 工具链本机打 NSIS 安装包，静默安装后启动、绑定、跑通 Claude Code 一轮，全程没有弹出控制台窗口（子进程统一经 `gonggong::proc` 带 `CREATE_NO_WINDOW` 启动）。`cargo test -p gonggong --lib` 在 Windows 上 211 过 7 失败，均为测试本身的平台假设（Unix 绝对路径、Windows 非法文件名、全局 `core.autocrlf=true` 影响测试仓库），尚未修。集成测试未在 Windows 上跑。

## 注意
脚本通过 `docker cp` 把源码传进容器，不用目录挂载。本机 Docker Desktop 的 API 代理启动容器时会卡住，这次是临时把 `DOCKER_HOST` 指向 `~/Library/Containers/com.docker.docker/Data/docker.raw.sock` 跑的，脚本本身不依赖这个设置。
