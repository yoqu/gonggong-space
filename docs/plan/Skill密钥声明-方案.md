# Skill 密钥声明与配置引导 方案（v1.0 定稿待确认）

> 状态：2 轮评审已合并（2026-11-18），待姜维川确认。承接 `团队密钥-方案.md` 二期「Skill 声明密钥并做缺失检查」。

## 1. 问题

以市场 Skill `dw-query` 为例：它要每人自己的 `DW_MANAGER_API_KEY`（正式，必需）和 `DW_MANAGER_TEST_API_KEY`（测试，可选），但只写在 SKILL.md 正文里。

| 环节 | 现状（代码核实） | 后果 |
|---|---|---|
| 创建/发布 | 只有插件清单 `secrets: string[]`（仅名字）；Skill 包没有声明位置 | 平台不知道 Skill 要密钥，市场详情、审核都看不到 |
| 引入 | 引入流程不碰密钥；密钥定义要管理员另去设置页手工建，名字、mode 全靠猜 | 引入完就「坏着」 |
| 运行 | Agent 读正文才发现要密钥 → `secret_request`；若本群没有该名字的定义，工具直接回「新定义只能由管理员在设置里添加」（`agent-tools/secrets.ts:74`） | 用户跑到一半才知道，且常常死路 |
| 填写 | 「我的密钥」只列已有定义，没有「为什么要填、去哪申请」 | 成员不知道要填、不知道怎么拿 Key |

## 2. 目标与底线

密钥需求**在创建时声明** → **发布/审核时可见** → **引入时由人确认建好定义** → **成员各自被引导填写** → **运行前就知道缺什么**。值的存储、加密、注入、打码沿用团队密钥一期，不改。

安全底线（限本方案的 Skill/插件声明链路）：**声明不是授权**。定义只在人确认的动作里创建——管理员引入/升级、管理员点建定义卡片、成员为自己的个人引入填值；Agent 不能建定义、写值、改模式、扩大 Bot 授权。现有 Agent 的 MCP 创建/更新会为未定义的引用建空定义（`mcp/secrets.ts:153`），不在本期范围。

## 3. 声明格式（创建时规定）

统一结构 `SecretRequirement`（`packages/protocol`），Skill 和插件共用：

```yaml
# SKILL.md frontmatter
secrets:
  - name: DW_MANAGER_API_KEY
    title: 数仓 Manager Key（正式）
    description: 在 Manager「个人中心 → API Key」签发，只读权限即可
    url: https://…/manager/keys        # 可选：申请入口，只允许 https
    placeholder: dwk_…                 # 可选：输入框占位，提示格式
    mode: personal                    # 建议模式：personal | shared | shared_overridable
    required: true                    # false = 可选（如测试环境 Key）
  - name: DW_MANAGER_TEST_API_KEY
    title: 数仓 Manager Key（测试）
    mode: personal
    required: false
```

- 上传时校验：名字合法且不重复、≤10 个、不和平台保留名冲突、`url` 必须 https。
- **声明来源**：市场版本写进版本快照 `manifest`；手写 Skill（`skill_versions` 没有 manifest）每次从该版本原始 `SKILL.md` 解析。都**不需要数据库迁移**。`skill_create`/`skill_update` 工具描述写明格式。
- **顶层 `secrets` 是共工扩展，不宣称符合 Agent Skills 规范**（规范 `metadata` 只允许 string→string，参考校验器拒绝未知顶层字段；Codex 不拒、Gemini CLI 只取 `name`/`description`，Claude Code 本地未确认）。
  - 共工内始终保存原始文件与**源摘要**，编辑、审核、回滚、发布去重都用源摘要（只改声明也算新版本）。
  - 对外兼容导出时剥离 `secrets`；共工内的下载再上传保留原文件，不丢声明。
  - 运行包默认保留原文件。若三端实测有适配器拒绝，再用同一套规则生成剥离后的运行文件和**运行摘要**，`run.start` 与 daemon 下载都用运行摘要，保证一致。
  - 验收：在项目实际使用的三个适配器版本上测「发现 + 调用」，不只看退出码。
- **插件清单兼容**：`secrets` 接受字符串（= `{name, mode: shared, required: true}`）或对象，发布、预检、GitHub 导入共用一个解析入口归一化（含直接读 JSON 的旧快照）。新写入的 manifest 直接存兼容形状：`secrets` = 必需密钥名列表，`secretSpecs` = 全量声明，透传 manifest 的 DTO 也不会把对象数组给旧客户端。`pluginBlocker`、MCP 引用校验、Web `model.ts` 改用归一化结果。**一期在解析入口拒绝 MCP 配置引用 `required: false` 的密钥**。`PluginRef` 与 MCP 下发形状不变，daemon 不改。

## 4. 发布与审核

- 市场详情页、引入对话框加「需要的密钥」区块：title、用途、必需/可选、建议模式、申请链接（外链图标 + 目标域名，如「前往 manager.example.com 申请」，标明发布者）。
- 审核 diff 里声明变化单独高亮（新增必需密钥 = 已引入方升级后会缺值）。

## 5. 引入与升级：由管理员确认建定义

- 群管理员/团队 admin 引入（或审批「申请引入」）时，对话框逐项列出声明与目标层现状。**名字不可改**（脚本读原变量名）。按情况给具体选项：
  - **没有同名定义** → 默认勾选「创建定义」，描述、mode 按声明预填可改；`shared` 类可当场填统一值，也可稍后。
  - **同名定义在上一层**（如团队层已有、当前是群引入）→ 并排显示两边用途；单选「复用团队层现有定义」/「在本群新建同名定义（仅本群生效，覆盖团队层）」。
  - **同名定义就在目标层** → 并排显示；单选「共用现有定义（说明和模式不变）」/「取消引入」。说明或 mode 不同时高亮「用途可能不一致」。
- 定义建在引入目标层：群 → 群层；仓库 → 所属团队层；团队 → 团队层。创建按 `(层, 名字)` 幂等，并发引入时后到的看到「已有」走上面的选项。
- **个人引入**（已拍板：团队层 `personal`）：个人安装没有团队，公共 Skill 可在多个团队生效。所以不在安装时建，而在**该用户在某群用到它、所属团队没有同名定义时**，待办条对本人显示，本人填写时在**这个群所属团队**建 `personal` 定义并写值。不用发布者团队，不遍历用户所在的所有团队。
- **升级**：
  - 手动升级或改固定版本：确认弹窗显示「密钥变更」（新增 / 删除 / 必需性变化），新增项同上一键创建。
  - 跟随最新版的安装（`listVersion` 自动推进）、维护者自测草稿：照常跟随，**不自动建定义**；缺的定义由第 6 节管理员待办条与第 7 节建定义卡片补上。
  - 管理员没勾选或事后删掉的定义，平台不会再自动建回来。
- **卸载**不删定义和值（其他 Skill 可能仍在用），弹窗提示「以下密钥定义可在设置里清理」。

## 6. 成员填写引导（各自填写）

- **群内待办条**（唯一主动引导，已拍板）：输入框上方**单行**，只对还有必需项要配的人显示，个人值和（管理员的）统一值、待建定义合并计数：「本群有 3 个密钥待你配置 · 去配置 ×」。计数**只算必需项**。
- 「×」= 推迟 24 小时；以下情况立即重新显示：缺的集合变了（如升级新增），或该成员发起的运行因缺这个密钥出了卡片。待办条与群内卡片读同一份服务端状态，任一处填完，另一处随之更新。
- 群设置 Skill 列表里，有声明的 Skill 旁常驻「配置密钥」入口，推迟期间也能主动去填。
- 「去配置」打开填写弹窗：按 Skill 分组，标签区分「个人密钥」「本群统一密钥 · 管理员」「待创建定义 · 管理员」；每项显示 title、description、申请链接、placeholder，`SecureField` 输入；可选项收在「可选配置」折叠区。
- 个人值按 `团队 + 用户 + 名字` 存，同团队一人多群只填一次；弹窗写明「此值在本团队所有使用同名密钥的群和 Skill 中通用」，已填项显示「已配置 · 尾号 xxxx · 更新于 …」。
- 「允许在他人机器上的 Bot 使用」开关：若本群有 Bot 跑在别人的电脑上，开关旁直接点名：「本群 @共字君 运行在其他成员的电脑上，打开后它才能使用此密钥」。

## 7. 运行时：提前知道缺什么

- **缺失提示**：`scheduler.ts` `buildRunStart` 用本轮实际生效的 Skill **版本**声明与 `secrets.env` 算差集，写进 `note`（同时进入 `context` 与 `fallbackContext`），不放 `bot.systemPrompt`。只带 Skill 名、变量名和状态，不带值和发布者原文。状态与 Agent 的处理：

  | 状态 | Agent 处理 |
  |---|---|
  | 没有定义（但在声明里） | `secret_request` → 管理员建定义卡片 |
  | 有定义、没填 | `secret_request` → 填写卡片 |
  | 已填，但不允许他人电脑上的 Bot 用 | 不发卡，告诉用户：「你已配置 X，但尚未允许运行在他人电脑上的 @Bot 使用；请到设置 →『我的密钥』打开『允许在他人机器上的 Bot 使用』」 |
  | 定义已停用 / 已过期 / 未授权给本 Bot | 不发卡，说明具体原因，请对应层管理员处理 |

- **建定义卡片**：
  - 发卡时服务端把实际生效的 Skill 来源、版本、引入目标、密钥名、目标层写进卡片消息 `messages.meta`（服务端写，免迁移）。
  - 卡片点名能处理的人：「等待群管理员（@张三、@李四）确认创建定义，创建后会为你发填写入口」；目标层是团队且群里没有团队管理员时，写出团队管理员名字并提示去团队设置处理。
  - 点击时按**当前审批人**校验该层管理员权限，不认发起人、Bot 或收件人名单。Skill 已升级、卸载、被覆盖，或期间出现同名定义，旧卡失效。确认后创建定义，再按模式发填写卡片；并发两张卡时后到的失效，不重复发填写卡片。
  - 平台内置 Skill（无引入记录）不发卡，提示请平台管理员处理。
  - 同一「目标层 + Skill 版本 + 密钥名」已有未处理卡片时复用，不重复打扰。
- **填写卡片绑定定义**：发卡时把每个名字对应的定义 ID、层和模式写进 `messages.meta`。提交时同时校验原 ID 与当前运行的解析结果，重验成员身份、填写权限、有效期和 Bot 授权，校验、写值、标记已填放在同一事务；不一致即提示「定义已变更，请重新申请」。本期之前发出的未填卡没有快照，统一提示重新申请或去设置填写；已填卡保留只读历史。
- 填写后沿用现有衔接：满足续跑条件（直接触发的首跳）时群里提示「已填写密钥，{bot} 继续处理」并自动续跑，否则提示重新 @。

## 8. 已拍板（姜维川 2026-11-18）

1. 个人引入的 Skill 要密钥：若群/团队都没有定义，在**团队层自动建 `personal` 定义**（只建定义不填值，团队 admin 可见可删），不加 `user` 层，无迁移。（落地方式见第 5 节：在用户实际使用的群所属团队，随本人填写创建。）
2. 声明位置：**SKILL.md frontmatter 顶层 `secrets`**。
3. 引导：只做**群输入框上方待办条**（只对没填的人），不发通知、不加徽标。
4. 缺必需密钥时 Skill **照发**，靠运行上下文提示 + `secret_request` 卡片（与插件「缺密钥不下发」不同，有意为之）。

## 9. 分期与验收

| 期 | 范围 |
|---|---|
| 一期 | `SecretRequirement` 协议 + Skill/插件解析归一化；源摘要/导出剥离；市场详情与引入/升级对话框；待办条 + 填写弹窗 + Skill 列表入口；运行 `note` 四种状态；建定义卡片；填写卡片绑定定义 ID；`dw-query`、`feishu-devops-cli` 补声明 |
| 二期 | 审核 diff 高亮声明变化；预检扫描漏声明变量（`os.environ["X"]` 等，只提示不拦截）；MCP 引用可选密钥；收紧 Agent MCP 链路建空定义 |

一期端到端验收用 `dw-query`：引入前可见声明 → 管理员一键建定义 → 成员看到待办条并填写 → 下一轮可用；不填测试 Key 不影响正式路径。

补测：同名不同用途（上一层 / 同层）、个人引入跨团队、跟随版本新增必需项、管理员删除后不复活、卸载不连带删除、只改声明的版本不被去重、建定义卡并发与过期、发卡后成员退群 / 管理员撤权 / Bot 授权变化时旧卡不能提交、旧卡无快照、三适配器发现与调用。

涉及：protocol、server、web、desktop（复用 web 组件），不涉及 daemon 与数据库迁移。
