# Skill 密钥声明与配置引导 方案（v0.3）

> 状态：评审中（2026-11-18，第 1 轮意见已合并，待第 2 轮）。承接 `团队密钥-方案.md` 二期「Skill 声明密钥并做缺失检查」。

## 1. 问题

以市场 Skill `dw-query` 为例：它要每人自己的 `DW_MANAGER_API_KEY`（正式，必需）和 `DW_MANAGER_TEST_API_KEY`（测试，可选），但只写在 SKILL.md 正文里。

| 环节 | 现状（代码核实） | 后果 |
|---|---|---|
| 创建/发布 | 只有插件清单 `secrets: string[]`（仅名字）；Skill 包没有声明位置 | 平台不知道 Skill 要密钥，市场详情、审核都看不到 |
| 引入 | 引入流程不碰密钥；密钥定义要管理员另去设置页手工建，名字、mode 全靠猜 | 引入完就「坏着」 |
| 运行 | Agent 读正文才发现要密钥 → `secret_request`；若本群没有该名字的定义，工具直接回「新定义只能由管理员在设置里添加」（`agent-tools/secrets.ts:74`） | 用户跑到一半才知道，且常常死路 |
| 填写 | 「我的密钥」只列已有定义，没有「为什么要填、去哪申请」 | 成员不知道要填、不知道怎么拿 Key |

## 2. 目标与底线

密钥需求**在创建时声明** → **发布/审核时可见** → **引入时由人确认建好定义** → **成员各自被引导填写** → **运行前就知道缺什么**。值的存储、加密、注入、打码沿用团队密钥一期，不改。

安全底线：**声明不是授权**。定义只在人确认的动作里创建（引入、升级、管理员点卡片）；Agent 任何时候都不能建定义、写值、改模式、扩大 Bot 授权。

## 3. 声明格式（创建时规定）

统一结构 `SecretRequirement`（`packages/protocol`），Skill 和插件共用：

```yaml
# SKILL.md frontmatter
secrets:
  - name: DW_MANAGER_API_KEY
    title: 数仓 Manager Key（正式）
    description: 在 Manager「个人中心 → API Key」签发，只读权限即可
    url: https://…/manager/keys        # 可选：申请入口，只允许 https
    placeholder: dwk_…                 # 可选：输入框占位，提示格式
    mode: personal                    # 建议模式：personal | shared | shared_overridable
    required: true                    # false = 可选（如测试环境 Key）
  - name: DW_MANAGER_TEST_API_KEY
    title: 数仓 Manager Key（测试）
    mode: personal
    required: false
```

- 上传时校验：名字合法、≤10 个、不和平台保留名冲突、`url` 必须 https；声明写进版本快照 `manifest`，**不需要数据库迁移**。手写 Skill（`skills` 表）同样解析 frontmatter，`skill_create`/`skill_update` 工具描述写明格式。
- **顶层 `secrets` 是共工扩展，不宣称符合 Agent Skills 规范**（规范 `metadata` 只允许 string→string，参考校验器拒绝未知顶层字段）。上游源码：Codex 反序列化不拒未知字段，Gemini CLI 只取 `name`/`description`；Claude Code 本地未确认。处理：
  - 对外导出（下载、打包给 claude.ai / Skills API）时剥离 `secrets`；
  - 下发给 daemon 的运行包默认保留；若验收发现某适配器拒绝，改为**上传时生成剥离后的运行文件再算摘要**，不在下载时临时改字节沿用旧摘要；
  - 验收：在项目实际使用的三个适配器版本上测「发现 + 调用」，不只看进程退出码。
- **插件清单兼容**：`secrets` 接受字符串（= `{name, mode: shared, required: true}`）或对象，**在入口统一归一化**（含直接读 JSON 的旧快照）；接口响应保留旧的 `secrets: string[]`，结构化声明另用 `secretSpecs` 增量下发，旧客户端不受影响。`pluginBlocker`、MCP 引用校验、Web `model.ts` 改用归一化结果。**一期禁止 MCP 配置引用 `required: false` 的密钥**（否则缺值会被替换成空字符串）。`PluginRef` 与服务端生成的 MCP 配置契约不变，daemon 不改。

## 4. 发布与审核

- 市场详情页、引入对话框加「需要的密钥」区块：title、用途、必需/可选、建议模式、申请链接（外链图标 + 目标域名，如「前往 manager.example.com 申请」，标明发布者）。
- 审核 diff 里声明变化单独高亮（新增必需密钥 = 已引入方升级后会缺值）。

## 5. 引入与升级：由管理员确认建定义

- 群管理员/团队 admin 引入（或审批「申请引入」）时，对话框逐项列出声明与本群现状：
  - **没有同名定义** → 默认勾选「创建定义」，描述、mode 按声明预填可改；**名字不可改**（脚本读的是原变量名）；`shared` 类可当场填统一值，也可稍后。
  - **已有同名定义** → 并排显示「Skill 声明的用途」与「现有定义的说明、来源层、mode」；说明或 mode 不同就高亮「用途可能不一致，请确认是否复用」。复用与否由管理员决定，不自动改现有定义。
- 定义建在引入所在层：群引入 → 群层，团队/仓库引入 → 团队层；个人引入 → 团队层 `personal`（已拍板）。
- **升级**：确认弹窗显示「密钥变更」（新增 / 删除 / 必需性变化），新增项同上可一键创建。管理员没勾的、事后删掉的，平台不会再自动补建。
- **卸载**不删定义和值（其他 Skill 可能仍在用），只在弹窗提示「以下密钥定义可在设置里清理」。
- 并发引入两个声明同名密钥的 Skill：创建按 `(层, 名字)` 幂等，后到的看到「已有」走复用比对。

## 6. 成员填写引导（各自填写）

- **群内待办条**（唯一主动引导，已拍板）：输入框上方**单行**，只对还没填必需个人值的人显示，多项聚合：「本群有 2 个 Skill 需要你配置 3 个密钥 · 去配置 ×」。计数**只算必需项**。
- 「×」= 推迟 24 小时；以下情况立即重新显示：缺的密钥集合变了（如升级新增必需项），或该成员发起的运行因缺这个密钥而出了填写卡片。
- 个人值按 `团队 + 用户 + 名字` 存，同团队一人多群只填一次，别的群不再提示；弹窗明确写「此值在本团队所有使用同名密钥的群和 Skill 中通用」，已填项显示「已配置 · 尾号 xxxx · 更新于 …」。
- 「去配置」打开填写弹窗：按 Skill 分组，每项显示 title、description、申请链接、placeholder，`SecureField` 输入，带「允许在他人机器上的 Bot 使用」开关；可选项收在「可选配置」折叠区。
- 统一值缺失时，待办条只对该层管理员显示「dw-query 缺统一值 · 去填写」。

## 7. 运行时：提前知道缺什么

- **缺失提示**：`scheduler.ts` `buildRunStart` 用本轮实际生效的 Skill **版本**声明与 `secrets.env` 算差集，写进 `note`（同时进入 `context` 与 `fallbackContext`），不放 `bot.systemPrompt`。只带 Skill 名、变量名和状态，不带值和发布者原文。状态分三种，Agent 处理不同：
  - 没填 → 用到时 `secret_request` 发卡；
  - 已填但不允许这台机器用 → 告诉用户去「我的密钥」打开开关，不发卡；
  - 定义缺失、停用或未授权给本 Bot → 告诉用户请管理员处理。
- **`secret_request` 遇到没有定义的名字**：若该名字在本群生效 Skill 的声明里，不再直接拒绝，而是给**该 Skill 引入层的管理员**发一张「按声明创建定义」卡片（显示来源 Skill、声明内容），管理员点确认才创建，创建后再按模式向成员发填写卡片。不在声明里的名字维持原拒绝。Agent 全程不建定义。
- **卡片写对定义**：提交时改用与 `secret_request` 相同的解析（按运行的 Bot、有效期、授权）定位定义，不再按名字取最低层；定位到的定义和发卡时的层或模式不一致就提示「定义已变更，请重新申请」。
- 填写后的衔接沿用现有逻辑：卡片刷新为已填写，群里提示「已填写密钥，{bot} 继续处理」并自动续跑（中继任务提示重新 @）。

## 8. 已拍板（姜维川 2026-11-18）

1. 个人引入的 Skill 要密钥：若群/团队都没有定义，在**团队层自动建 `personal` 定义**（只建定义不填值，团队 admin 可见可删），不加 `user` 层，无迁移。
2. 声明位置：**SKILL.md frontmatter 顶层 `secrets`**。
3. 引导：只做**群输入框上方待办条**（只对没填的人），不发通知、不加徽标。
4. 缺必需密钥时 Skill **照发**，靠运行上下文提示 + `secret_request` 卡片（与插件「缺密钥不下发」不同，有意为之）。

## 9. 分期与验收

| 期 | 范围 |
|---|---|
| 一期 | `SecretRequirement` 协议 + Skill/插件解析归一化；导出剥离；市场详情与引入/升级对话框；待办条 + 填写弹窗；运行 `note` 缺失提示；`secret_request` 管理员建定义卡片；卡片按运行解析定义；`dw-query`、`feishu-devops-cli` 补声明 |
| 二期 | 审核 diff 高亮声明变化；预检扫描漏声明变量（`os.environ["X"]` 等，只提示不拦截）；MCP 引用可选密钥 |

一期端到端验收用 `dw-query`：引入前可见声明 → 管理员一键建定义 → 成员看到待办条并填写 → 下一轮可用；不填测试 Key 不影响正式路径。补测：同名不同用途、个人引入与群引入并存、升级新增必需项、管理员删除后不复活、卸载不连带删除、三适配器发现与调用。

涉及：protocol、server、web、desktop（复用 web 组件），不涉及 daemon 与数据库迁移。

## 10. 第 1 轮评审处理（共字君Codex、Antigravity CLI）

| 意见 | 处理 |
