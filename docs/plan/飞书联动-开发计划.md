# 飞书联动开发计划（草案）

目标：Bot 可以在飞书群里被 @ 和使用。和 Agent 有交互的消息、卡片在共工与飞书之间双向互通；普通闲聊不同步。共工数据库是唯一来源。

## 1. 已确认决策

| # | 项 | 结论 |
| --- | --- | --- |
| F1 | 应用模型 | **每个 Bot 一个飞书自建应用**（Bot 应用）+ **整个系统一个主应用**（登录发生在选择团队之前，所以主应用不能挂在团队下）。飞书没有创建应用的开放接口（待 S0 核实），所以是「绑定已有应用」：在开发者后台建好后，把 App ID / Secret 填到共工 |
| F2 | 主应用职责 | 飞书一键登录与身份认证（§2.0）；把共工侧人类的 @Bot 消息发到飞书（用户授权过就以本人身份发，否则代发「张三：…」）；群绑定指令 |
| F3 | Bot 应用职责 | 接收 @自己 的消息作为触发；以自己的身份发回复、运行卡片、提问和审批卡片；接收卡片回调和撤回事件 |
| F4 | 同步范围 | **只同步和 Agent 有交互的消息**：@Bot 的消息、回复或引用 Bot 消息的消息、卡片作答和审批、Bot 的全部输出。普通消息两边都不同步 |
| F5 | Agent 读飞书上下文 | 不保存。内置 MCP 新增 `list_feishu_messages`，用**触发者本人的身份**实时读取飞书群近期消息，只返回给 agent |
| F6 | 触发资格 | 只有完成共工账号认证、而且是共工对应群成员的飞书用户才能触发、作答、审批。未认证或不是群成员的人收到提醒卡片，不触发 |
| F7 | 撤回 | 两端双向同步。运行排队中：作废；运行已开始：**继续运行**（与现有 `recall.ts` 一致） |
| F8 | 编辑 | 一期要做，范围限于「发给 Bot 的消息」。运行排队中：用新内容替换输入；运行已开始：停止当前运行，用新内容重新触发，运行卡片注明「消息已编辑，已重新运行」。共工本身要先新增编辑功能 |
| F9 | 回链 | 卡片上的「查看过程 / 预览」链接到共工 Web 的对应页面，地址取 server 对外地址配置。一期只在内网可用，server 部署上线后改配置即可 |
| F10 | 接收方式 | 飞书长连接（WebSocket），server 不需要公网回调地址。每个应用一条连接，由 server 进程统一维护 |
| F11 | SDK | `@larksuiteoapi/node-sdk`（`npm view` 核实为 1.74.0）。接入前先按官方文档核对长连接、卡片回调、CardKit 的 API |
| F12 | 凭证存储 | App Secret、用户 token 用 `lib/seal.ts` 加密后存库 |
| F13 | 飞书登录 | 登录页增加「飞书登录」按钮，走主应用 OAuth。**登录即认证**：一次完成 F6 要求的身份绑定；用密码登录的用户可以在个人设置里绑定飞书 |
| F14 | 首次飞书登录 | 已绑定飞书：直接登录。未绑定：进入选择页，二选一：「绑定已有账号」（输入密码验证后绑定），或「新建账号」（姓名取飞书姓名，账号取飞书企业邮箱前缀，冲突时加后缀，不设密码），新账号按现有规则加入默认团队 |
| F15 | 开户开关 | 系统参数 `feishuAutoSignup`（默认开）：主应用是企业自建应用，只有本企业成员能完成授权，所以飞书新建账号不受 `registrationOpen` 限制。关闭后只能「绑定已有账号」或凭邀请链接注册 |
| F16 | 回链免登 | 在飞书客户端内打开回链时，没有登录态就自动跳转飞书授权并返回原页面，用户无需手动登录 |
| F17 | 配置位置 | 主应用凭证、开户开关放在管理后台（仅系统管理员）。没有配置主应用时，登录页不显示飞书按钮，飞书联动整体不可用 |

## 2. 关键流程

### 2.0 飞书登录
1. 登录页 →「飞书登录」→ 跳转主应用授权页（`state` 防 CSRF，携带登录后要返回的页面）→ 回调 `/api/auth/feishu/callback` 用 code 换取 user token，再取用户信息（union_id、user_id、姓名、邮箱、头像）。
2. 按 union_id 查 `feishu_identities`：命中就签发 web session（复用 `signIn`）；没命中进入 F14 的选择页（凭一次性 ticket 完成后续步骤，ticket 10 分钟有效）。
3. 账号已停用（`disabledAt`）时拒绝登录，和密码登录一致。
4. 同一个共工账号只能绑定一个飞书身份，同一个飞书身份也只能绑定一个共工账号；在个人设置里可以解绑（解绑后需要有密码才能继续登录，否则不允许解绑）。
5. Desktop 和 CLI 仍然使用 Web 生成的接入码，不受影响。

### 2.1 飞书 → 共工（触发）
1. 用户在飞书群里 @BotX，BotX 的应用收到 `im.message.receive_v1`。
2. 用 `chat_id` 找到绑定的共工群；发送者经 union_id（或 user_id）映射到共工用户。映射失败或不是群成员时，回复提醒卡片并结束（F6）。
3. 按飞书 `message_id` 查映射表：
   - 第一次出现：作为共工用户消息写入（`postMessage`），`meta.mentions=[BotX]`，再走现有 `triggerRuns`；
   - 已经存在（同一条消息还 @ 了其他 Bot，各自的应用都会收到）：只追加该 Bot 的 mention，并为它创建运行。
4. 附件通过消息资源接口下载，存成共工附件。

### 2.2 共工 → 飞书
| 内容 | 由谁发 | 方式 |
| --- | --- | --- |
| Web 端 @Bot 的消息 | 主应用 | 用户已授权：以用户身份发；未授权：代发「张三：…」 |
| 运行卡片 | Bot 应用 | 回复触发消息（形成引用）。状态原地更新，节流不超过 1 次/2 秒。**不开启流式模式**（流式期间不能响应按钮回调，10 分钟后还会自动关闭） |
| 最终回复 | Bot 应用 | Markdown 卡片 + 回链按钮；超长内容截断后挂回链 |
| 提问和审批卡片 | Bot 应用 | 按钮通过 `card.action.trigger` 回调到共工，复用 `answerQuestions` / `decideApproval`，操作人按 F6 校验。在 Web 端处理后，飞书卡片同步更新为「已由某某处理」 |

### 2.3 防回环与去重
- 消息映射表记录每一条外发消息的飞书 `message_id`，收到同 ID 的事件直接丢弃。
- 发送者是我们自己任何一个应用的事件，一律丢弃。
- Bot 之间的接力只在共工内部发生，飞书只展示结果。

### 2.4 撤回和编辑
| 起点 | 撤回 | 编辑 |
| --- | --- | --- |
| 飞书 | `im.message.recalled_v1` → `recallMessage` 语义 | **待核实是否有编辑事件**。没有的话，提示「飞书侧编辑无效，请撤回后重发」 |
| 共工 | 撤回已映射的飞书消息（以用户身份发的用用户 token，代发的由主应用撤回） | 调飞书编辑消息接口（最多 20 次，受企业设置的可编辑时间限制） |

### 2.5 群绑定
1. 群管理员在共工的「群设置 → 飞书」里，从主应用所在的飞书群中选一个，一对一绑定。
2. 检查共工群里各 Bot 的应用是否已在飞书群中，缺少的提示拉入（能否用 API 自动拉入，待核实）。
3. 解绑后停止所有同步，历史映射保留。

### 2.6 `list_feishu_messages`（内置 MCP）
- 入参：`limit?`（默认 20，最大 50）、`before?`（飞书消息时间）。
- 鉴权沿用《内置MCP》C5：以正在进行的运行为锚，使用**该运行触发者**的主应用 user token；读取范围只限当前共工群绑定的飞书群。
- 输出格式与 `list_messages` 一致：`[时间] 作者: 正文`，不写入数据库。
- 系统提示词：只在群已绑定飞书时追加一句工具使用说明。

## 3. 数据模型

| 表 | 关键字段 |
| --- | --- |
| `feishu_apps` | `team_id`、`kind`（`main` \| `bot`）、`bot_id`（kind=bot 时）、`app_id`（唯一）、`app_secret`（加密）、`status`（`connected` \| `error`）、`error` |
| `feishu_identities` | `user_id`（唯一）、`union_id`（唯一）、`user_id_feishu`、`access_token` / `refresh_token`（加密）、`expires_at` |
| `feishu_chats` | `group_id`（唯一）、`chat_id`（唯一）、`bound_by`、`bound_at`、`unbound_at` |
| `feishu_message_links` | `message_id`、`feishu_message_id`（唯一）、`app_id`、`direction`（`in` \| `out`）、`kind`（`message` \| `run_card` \| `question` \| `approval`）、`run_id?` |
| `messages` | 新增 `edited_at` |
| `users` | `password_hash` 改为可空（飞书新建账号没有密码；密码登录遇到空值直接判定失败） |

## 4. 权限清单

| 应用 | 权限 | 事件 / 回调 |
| --- | --- | --- |
| 主应用 | 网页应用登录授权（OAuth 重定向地址需在安全设置中登记）、获取用户基本信息和邮箱、`im:message`、`im:message.send_as_user`、`im:message.group_msg:get_as_user`（用户身份读取上下文）、读取群信息、获取用户 union_id | 无（如果用 `@主应用 /bind` 方式绑定，再加 @ 权限） |
| Bot 应用 | `im:message.group_at_msg:readonly`、`im:message:send_as_bot`、`cardkit:card:write`、读取消息资源（附件） | `im.message.receive_v1`、`im.message.recalled_v1`、`card.action.trigger` |

不申请「获取群组中所有消息」敏感权限。

## 5. 需要 S0 实测确认的事项

1. 能否用开放接口创建自建应用（预期不能）。
2. 同一条消息在不同应用看到的 `message_id` 是否一致（2.1 第 3 步依赖这一点）。
3. 同一企业的多个自建应用之间 union_id 是否一致；不一致就改用 user_id（每个应用都要加 `contact:user.employee_id:readonly`）。
4. 只有 @ 权限时，「回复 Bot 消息但没有 @」能否收到。收不到的话，F4 的触发条件收窄为必须 @。
5. 飞书侧编辑消息有没有推送事件。
6. 「仅特定人可见」卡片能否用于提醒认证（不能就改为在话题里 @ 本人回复）。
7. 能否用 API 把 Bot 应用拉进群。
8. `im.message.recalled_v1` 需要的 `im:message:readonly` 是否需要管理员审批。
9. 群消息发送的频率限制，以及多个 Bot 并发时是否需要排队。
10. OAuth 重定向地址是否允许内网 http 地址；当前推荐的 OAuth 授权和换 token 接口版本。
11. 飞书客户端内置浏览器打开授权页时，是否不用确认、直接通过（F16 体验依赖这一点）。

## 8. 飞书后台配置清单（开发已按此实现，真实环境待配置）

所有应用：开启「机器人」能力；事件与回调的订阅方式选**长连接**；每次修改后创建版本并发布（需要企业管理员审核）。

**主应用**
- 安全设置 › 重定向 URL：`<对外地址>/api/auth/feishu/callback`（对外地址在共工管理后台 › 飞书里配置）。
- 权限（应用身份）：`im:message:send_as_bot`（代发、撤回、编辑自己的消息）、`im:chat:readonly`（列出所在群）、`im:chat.members:write_only`（把 Bot 应用拉进群）。
- 权限（用户身份，授权时会请求这些 scope，必须全部开通，否则授权报 20027）：`offline_access`（拿 refresh_token）、`contact:user.email:readonly`、`im:message`、`im:message.send_as_user`、`im:message.group_msg:get_as_user`；另需获取用户基本信息（union_id、open_id、姓名、头像）。
- 事件：无。

**每个 Bot 应用**
- 权限：`im:message.group_at_msg:readonly`、`im:message:send_as_bot`、`im:message:readonly`（撤回事件、下载附件、更新自己的卡片）、`im:chat:readonly`。
- 事件：`im.message.receive_v1`、`im.message.recalled_v1`。
- 回调：`card.action.trigger`（能否走长连接待实测）。

**实测时重点核对**：§5 各项；卡片 JSON 2.0 中下拉、多选、输入框、危险按钮的字段名；OAuth 换 token 端点（SDK 走 `oauth/v3/token`，文档推荐 `authen/v2/oauth/token`）。
