## 2. 技术架构（P1）

| 模块                  | 技术                                            | P1 职责                                                                                                                             |
| ------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `packages/protocol` | TypeScript + zod                              | Web ↔ 业务层、daemon ↔ 业务层的全部消息类型；每种消息附一份 JSON 示例，作为 Rust 端的契约测试用例                                                                    |
| `apps/server`       | Node.js + Fastify + ws + Drizzle + PostgreSQL | 账号、群、bot、消息路由、审批、提问、通知、审计、用量、文件镜像、运行过程存储（入库前脱敏）、定时清理                                                                              |
| `apps/web`          | React + Vite + TypeScript                     | 群聊三栏、运行卡片、侧边栏、输入框候选、群设置、管理后台、登录与绑定、通知与搜索                                                                                          |
| `crates/gonggong`       | Rust + tokio + agent-client-protocol          | daemon 核心 + `gonggong` CLI：连接与心跳、ACP 适配（Claude Code / Codex）、托管工作区、git 默认动作、/cd、会话恢复、并发与本机队列、内置「向群成员提问」MCP、附件落盘与 exclude、离线缓存与补传、自动升级 |

P1 不启动 Rust 同步服务；数据模型保留「群 → 多仓库」、群锁、权威版本等字段的扩展位。

## 3. 协作方式：纵向分工 + 全平台里程碑

- **全平台里程碑**：每个里程碑都要同时交付 Web、业务层、daemon 三端，并以一条真实端到端场景（浏览器 → 服务器 → 本机 daemon → 真实 agent → 回到浏览器）通过为结束标志。上一个里程碑没验收完，不开下一个。
- **纵向分工**：里程碑拆成若干「功能切片」，每个切片由一个子 agent 从头做到尾，包括协议、数据库、业务层、Web、daemon 和测试，而不是按前端 / 后端分人。
- **契约先行**：每个里程碑开始时，由主控（我）先统一定好本里程碑的协议消息和数据库表改动并合入主干，各切片在此基础上并行开发（各自在独立 git worktree 里），避免改同一批文件发生冲突。
- **TDD**：每个切片先写失败的测试（验收场景 → 集成测试 → 单元测试），再实现到测试通过。切片完成的标准：本切片测试全绿、全量测试不回归、lint 和类型检查通过。
- **主控集成**：合并各切片 → 跑全量测试 → 跑本里程碑的真实 E2E 和边缘场景清单 → 记录验收报告 → 进入下一个里程碑。

## 5. 测试与边缘场景（每个里程碑必须覆盖）

- **测试分层**：单元测试（vitest / cargo test）→ 集成测试（server 连真实 PostgreSQL 测试库；daemon 连假服务器；ACP 连真实 agent 或 Mock agent）→ E2E（Playwright + 真实三端 + 真实 agent + 本地 bare 仓库）。
- **边缘场景清单**（按里程碑补全后逐条自测）：
  - 连接：心跳丢失判离线、断线重连、协议版本不兼容、token 被吊销、绑定码过期 / 重复使用 / 输错 5 次
  - 运行：agent 崩溃、agent 卡死、ACP 协议错误、agent 未安装或版本过低、会话恢复失败、并发打满后排队、离线请求 30 分钟作废、同一 bot 在两个群里同时运行
  - 权限：非主人点审批、审批超时、范围外触发、接力链中途有一跳越权、full 档位名单校验
  - git：工作树不干净时不快进、分叉、clone 失败（没有凭据 / 地址错误）、/cd 目录的 remote 不一致、bot 在强制同步群被标记为不参与（P1 只需报错，不需要支持）
  - 输入：附件超过 50 MB / 超过 10 个、Codex 不支持图片时只落盘、skill 与系统命令重名、@ 不存在的 bot
  - 并发一致性：同一条消息被重复投递（幂等）、断线期间产生的事件补传后的顺序、两个浏览器页签同时审批

## 6. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 两个 ACP 适配器对会话恢复、取消后继续、图片、用量上报、可用命令的支持不对称（spec 风险 4、7、9） | M1 首先实测并写出能力矩阵；不支持的功能按 spec 退化（例如打断并追加退化为排队、用量显示「未上报」） |
| 真实 agent 测试慢、结果不稳定、消耗额度 | E2E 断言只看可观察的结果（文件是否生成、状态如何流转），不断言模型原文；提示词写得尽量确定；故障类场景交给 Mock agent |
| Windows 没有真机 | 如实标注为「交叉编译 + 单元测试」级别的验证，列入已知限制 |
| 命令输出里泄露密钥 | 入库前脱敏 + 30 天清理，用专门的测试用例覆盖 |
