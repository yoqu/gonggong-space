# 远程控制低延迟改造 · 设计

状态：**仅设计，暂不开发，优先级最低**（2026-09-30）。依据现有代码与推算，**没有实测数据**；开工前先做 R0 取得基线。

## 1. 背景与问题

现状（`结果预览-开发计划.md` P12、B1–B4）：

```
gg-cast(libwebrtc；macOS/Win H264，Linux VP8；3 层 simulcast，上限 90fps/20Mbps)
   └─ UDP 7882 / TCP 7881 ─→ LiveKit SFU（server 托管子进程）←─ 浏览器
信令：daemon / 浏览器 → server `/livekit`（只走信令）
输入：浏览器 publishData(reliable) → SFU → gg-cast → enigo
```

体感：局域网内也「卡卡的」。已知事实：

- 只测过本机回环，端到端 35–54 ms（§11）；LAN、公网、TURN 均未测。
- 生产环境 server 将部署在云上；开发阶段在内网，**内网测试会低估上云后的问题**。
- 用户场景：N 人围观、同一时刻只有 1 人控制，且必须看得出谁在操作。

## 2. 目标与非目标

目标

1. 控制者的操作跟手：点击到画面反馈、滚动、输入无明显停顿。
2. 围观保持中转（SFU），可扩展到 N 人，不受控制者进出影响。
3. 控制者与被控机器优先直连；直连不通回落，不能比现在更差。
4. 所有人看得见「谁在操作」；机器主人有常驻提示并可一键收回。
5. 无人围观时不占云端带宽。

非目标：自研传输协议（FEC、拥塞控制）；多人同时控制；音频；改变现有控制权申请/批准流程。

## 3. 卡顿的嫌疑（待 R0 验证）

「卡」更可能是**尾部抖动**而非平均延迟：稳态流水线本身约 40–55 ms。

| # | 嫌疑 | 位置 |
|---|---|---|
| A | 滚轮/按键/文字每次调用 `fresh()`（raise + xcap 枚举窗口）；`Down` 固定 sleep 20 ms | `crates/gg-cast/src/input.rs` |
| B | 所有输入走 reliable 有序通道，鼠标移动被丢包队头阻塞 | `apps/web/src/features/previews/live.ts` |
| C | ICE 落到 TCP 7881 或通告了错误网卡；`node_ip` 默认未设，上云必须设 | `apps/server/src/modules/live/livekit.ts` |
| D | 三层 simulcast 都按 90fps 编码，Retina 窗口负载高；采集是 `sleep` 轮询，默认 30fps | `crates/gg-cast/src/main.rs` |
| E | 观看端无 `jitterBufferTarget`；拥塞控制按视频会议调，起始码率低、切层等关键帧 | web / LiveKit |

## 4. 目标架构

```
                    ┌─ A 通路（围观）：SFU，simulcast 1–2 层，15–30fps，2–4 Mbps ─→ 围观者 N 人
gg-cast ── 采集 ────┤
                    └─ B 通路（控制）：直连 PeerConnection，单层高帧率 ────────────→ 控制者
                          ↑ 输入同走 B：move/wheel 走 unordered（maxRetransmits 0），down/up/key/text 走 reliable
```

规则

- 采集一次，编码两路；**B 只在有控制者且已连通时才编码**。
- **A 只在有围观者时发布**（沿用 `useWatch` 租约，区分角色）。只有控制者在看时，云端零媒体流量。
- B 未建立或中断：控制者改看 A，输入走 SFU 的 lossy/reliable 双通道（R1 的修复），A 临时拉高给控制者。
- 围观者永远只走 A。

### 4.1 授权

控制权仲裁沿用 `apps/server/src/modules/live/service.ts`（请求、批准、接管、收回、租约）。变化：

- 现在闸在 LiveKit（`canPublishData`）；直连后闸落在 **gg-cast**。
- server 为当前控制者签发 B 通路凭据：绑定 `userId`、preview、短有效期，SDP 的 DTLS 指纹纳入签名。gg-cast 只接受这一个 B 连接，没有凭据建不起通道。
- 换人、收回、租约过期：server 经 daemon 通知 gg-cast 立即断开 B。
- 信令走 server 现有 WebSocket；凭据与信令消息进 `packages/protocol`，daemon 消息同步 fixture 与 `protocol.rs`。

### 4.2 展示「谁在操作」

以 gg-cast **实际注入**的输入为准（所见即所控）：

1. **画面标签**：gg-cast 经 SFU lossy 通道下发指针的归一化坐标与当前控制者，围观端叠加带头像、名字的光标。
2. **顶栏**：沿用「X 正在控制」，加头像与已操作时长。
3. **切换提示**：控制权变更时画面上提示 1–2 秒。
4. **机器主人侧**：桌面端（共工.app）被控期间常驻「X 正在远程操作此机器」，一键收回。
5. **审计**：开始、结束、来源（直连/中继）、输入计数写入 `admin/audit.ts`。

### 4.3 云上部署要点

- LiveKit 媒体端口（UDP 7882、TCP 7881）必须公网直达；HTTP 负载均衡转发不了 UDP，nginx 只代理 `/livekit` 信令。
- 云主机 1:1 NAT：显式设置 `node_ip` 为弹性 IP（或 `use_external_ip: true`）。
- TURN：UDP 3478 + TLS 443；先复用 LiveKit 内置 TURN，中继占比高时拆出 coturn，就近部署。
- 被控机器上行有限（常见 20–50 Mbps）：A 路码率 2–4 Mbps、无人围观停发；B 路不占云带宽。
- 成本：云出口流量 = 围观人数 × A 码率；直连流量不经云。

## 5. 预期收益（推算，非承诺）

LAN 且 server 在 LAN 时（当前开发环境）：

| 改动 | 平均延迟 | 卡顿/尾部 |
|---|---|---|
| 输入拆通道 | ≈0 | 大（消除队头阻塞尖峰） |
| Injector 缓存窗口 | 点击 −20 ms；滚动/输入每事件 −5～30 ms（xcap 耗时未测） | 大 |
| 采集事件驱动 | −8～16 ms | 中 |
| 观看端 `jitterBufferTarget` 最小 | −20～50 ms | 中 |
| 修正 ICE 落 TCP | 若发生：−30～100+ ms | 最大 |
| 降低 simulcast 层数与帧率 | −0～10 ms | 中 |
| **直连** | **−1～5 ms，几乎无感** | 小 |

累计约 −30～40%（60–90 → 35–50 ms），最明显的是尖峰消失。

**server 在云上时，直连才是大头：**

| 场景 | 直连收益 |
|---|---|
| server 在云，两端在同一 LAN | −50～100 ms，且省云带宽 |
| 控制者在外网、机器在内网 | −20～60 ms（打洞成功时） |
| 对称 NAT 打洞失败 | 0（回落 TURN） |

打洞成功率保守估计 70–85%（第三方文章，非权威），其余靠 TURN。UU 远程宣称的约 95% 来自自建节点专网，不可照搬。

## 6. UU 远程的参考

官方页只确认：300+ 节点专网、最高 144 帧、码率上限 500 Mbps、真彩。其余来自第三方文章，低可信度：

- 信令 + STUN，UDP 打洞优先，失败走中继；同网段走内网地址。
- 自研 UDP 传输，FEC + 自研拥塞控制。
- H.265/AV1，动态码率，4:4:4。
- 专网中继来自游戏加速的基础设施，属商业壁垒。

可借鉴：直连优先、中继兜底；输入与视频分通道；拥塞控制按屏幕交互调。同类方案（RustDesk：UDP 打洞 → TCP 打洞 → ICE → relay；Parsec、Moonlight）结论一致。

## 8. 风险与开放问题

1. mDNS：LAN 纯 http 访问时浏览器只给 mDNS 候选，libwebrtc 原生端解析能力未验证（R3）。
2. B 路画质策略：屏幕内容需 `maintain-resolution`；控制中偏帧率还是清晰度需实测。
3. 切流闪断：需在 B 首个关键帧到达后再切。
4. 打洞与 TURN 占比取决于用户网络，TURN 节点位置和带宽要按实际分布规划。
5. 双路编码增加被控机器 CPU；B 与 A 的编码器实例、硬件编码并发上限需实测。
6. 上行不足时 A 与 B 争带宽，需要优先保障 B。
7. 本文所有收益数值均待 R0 验证，验证后回填。
